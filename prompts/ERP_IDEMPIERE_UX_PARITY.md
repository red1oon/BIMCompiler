## §LENS-REGISTER — action lenses against the AD rule (owner, 2026-11-09)
*"extra process lens should be avoided to comply for consistent maintainability. It is precisely the idea of legacy plugins to be adopting the AD."* · *"I know some earlier lens adoption broke that rule, but now is the opportunity to begin getting it right."*
**Why it matters beyond maintenance (owner, 2026-11-09):** *"Such AD layer allows the verb CLI scripting to work on it as an ORM."* What the dictionary defines, the verb layer can generate (tables → read/create/update/delete verbs; each `AD_Process` → a verb with its parameters; each DocAction → a verb with its legal WfMC transitions; computed columns → readable values), so it reaches the CLI, the AI menu and every channel at once and is counted in the NEURO roadmap's "X of 1,153 ERP actions" (`NEURO_SYMBOLIC_ORDER_CONTRACT.md` §22.6 D6). A lens action is invisible to all of that and needs a hand-made verb: one more reason it must move into the AD.
**Standing instruction:** any session that comes across a lens that registers record ACTIONS (`ctx.lens.register`, `AdLens.register`, a ⋯-rail action) adds a row here and a ⚠ AD-LAYER NOTE in that lens's own prompt file. View lenses (Graph/Kanban/Pivot/Chat dashboards, film overlays) re-present data, not processes, and are out of scope. Fix direction for every row: behaviour into the dictionary (`AD_Process` on the table/tab via the generic gear; computed values as `ColumnSQL` columns), the lens kept only as a shortcut to it or deleted. Generic guard to build once: a staged plugin's user actions are all enumerable from the AD (§BIMDOC-FEEDBACK).

## §BIMDOC-LEGACY SPEC (2026-11-11; owner: "The 2Pack zip is only pure metadata. The extra processes Java code has to be in the src folder of the OSGi component as any legacy should."; written before code)
**Aim:** the BIM Document model on a real iDempiere server, so the CAPEX dashboard's document tile (`bim-ootb/prompts/CAPEX_DASHBOARD.md` §5.36) has a legacy Source B. Two artefacts, kept apart:
1. **2Pack zip = pure metadata.** AD_Table `BIM_Document` + columns (incl. the virtual `ColumnSQL` progress columns on C_ProjectTask / C_ProjectPhase), AD_Reference + lists (discipline, file kind, the four states), AD_Window, the Project-window tabs (Task level and the project level of §BIMDOC-PROJTAB), AD_Menu, AD_Process rows (class NAMES only), window/process access, document type. To check at build time: that a virtual column (ColumnSQL set) is skipped by that DDL path.
2. **OSGi component, Java in its `src/` (as any legacy plugin).** What a pack cannot hold: (a) the model class for `BIM_Document` + its `IModelFactory`; (b) the DocAction implementation: Draft -> Issued for review -> Issued for construction, a deliverable needs a task, an older revision cannot be issued once a newer one is CO, completing a revision sets the older to Superseded (`Reversal_ID`), and the `§BIMDOC-CHAIN` before/after issued count; (c) the Export Register process class (JSON `[{no, rev, status, discipline, filekind, sha256, name}]`, latest revision of each deliverable + superseded rows: the contract the walker gate reads); (d) the Open process class. The rules in (b) are the twin's `bim_document.mjs` rules ported, not re-invented; the twin is the reference to diff against (TWIN RULE).
**Three ways to inject the AD metadata (owner 2026-11-11: "traditionally SQL migration scripts under the migration folder; and a 2Pack.zip can also take such scripts besides the PackOut.xml"). Checked in iDempiere source:**
- **PackOut.xml rows** (the dictionary as XML; matched by `_UU`, so a re-apply is idempotent). Our twin rows already carry stable UUs (`bimdoc-table-9541001` style).
- **SQL statements inside the pack.** `org.adempiere.pipo.handlers/.../SQLStatementElementHandler.java` reads `<statement>` with a `DBType` (so one pack can hold a Postgres and an Oracle form), and there are `SQLMandatoryElementHandler`, `ShellScriptElementHandler` and `ScriptJSR223ElementHandler` beside it. Found: SQL as ELEMENTS of PackOut.xml. Not found: a separate `.sql` file in the zip read by the pack-in; to check on the pilot before relying on it.
- **Migration scripts** `migration/iD13/postgresql/<yyyymmddHHMM>_<ticket>.sql` (core ships these; first statement `SELECT register_migration_script('<file>') FROM dual;`, plain DML, IDs >= 1000000 + `*_UU`). This is the route the CAPEX dashboard's legacy read types already use (`202611042300_CAPEX-WS-READ.sql`), and `erp/migration_apply.js` applies the same script to the twin through `convertSql`, so ONE script runs on both sides (TWIN RULE).
**Choice:** the dictionary (table, columns, lists, window, tabs, menu, process rows) = PackOut.xml generated from the manifest, because it is the portable, immutable-version form; seed or fix-up data the pack handles badly = a migration script (or a `<statement>` in the pack when it must travel inside the zip); the Java stays in the component `src/`. Which of the three a given row uses is stated per row in the spec's table when the build starts, never decided silently.
