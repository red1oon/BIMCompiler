## §8 ONE plugin or two? — and the separation of concern (owner, 2026-10-26: *"Study if the Team should combine with Replication as a singular plugin. And good separation of concern where it doesn't do any legacy core document function. It just manages multi user comm etc."*)
### §8.1 Answer: ONE runtime plugin, three layers inside it; the compiler stays outside
- **Why one.** Team and Replication share ONE signed log, ONE roster and trust anchor, ONE admission and ONE Visit cycle: the people strip, the chip, the plan reader and the executor map all read the same `CommStore`. Two plugins would need either two stores (two truths of who is in the team) or a plugin-to-plugin protocol over one store — a second implementation of one responsibility (AD-LAYER LAW 5). Legacy agrees: replication is ONE plugin with pluggable transports (`org.adempiere.replication`, §0).
- **The three layers (each knows less than the one above):** **L1 comm** — `common/comm/comm_*.js` + `op_versions.js`: seal, send, fetch, order, roster, admission, versions, trust. Knows NO table and NO host; shared by the ERP and the Modeller. **L2 replication** — the plan reader (`team_scope.js`) and the host adapter (`erp/team_sync.js` translate / project): which tables and columns travel, in which direction, for which role; reads the dictionary, names no table in code. **L3 team UX** — pairing, people strip, chip, pill, panel, guide.
- **Outside the plugin:** the **scriptor** (`build/scriptor/*`) is a BUILD tool; its output, the signed plan, is DATA the plugin loads (as a 2Pack is to an iDempiere plugin). The **comm relay / pipes** are a dumb post office (immutable twin principle (2)).
### §8.2 The boundary contract — what the plugin MAY and MAY NOT do
**MAY:** carry (seal, send, fetch); order and fold deterministically; **admit or refuse an op** by signature, roster, role and the signed policy (that is *who may send what* — a comm gate, not document behaviour); **project the results it receives into the local store as data** (a received Complete is its result rows, never re-executed, FL-8); **express team policy as CORE DATA** the core already understands (access rows, import rows, scheduler rows); run its own UX.
**MAY NOT:** run a DocAction, post, author a document, give a document its number, compute stock / price / tax, decide access in its own code, or show its own copy of a core message. Those are the core's — ported legacy classes (`ad_docfsm.js`, `model_*.js`, `erp/processes/*.js`, `ad_access.js`).

## §9 The local trigger instead of a scheduler, and the actions that CANNOT be purely separated (owner, 2026-10-26: *"Tell me which action can't be. … can't it be not so but internal listener or trigger locally say after POS Orderlines save, it triggers processes chain locally."*)
### §9.1 Yes — a local listener, and it is exactly legacy's mechanism
Legacy saves a received row with **`po.saveReplica(true)`** (`org.adempiere.replication/.../imp/ImportHelper.java:195,202,369,399`; `PO.java:2968-2973` = `setReplication(true)` + `saveEx()`), and the save then fires **distinct listener timings** — `TYPE_AFTER_NEW_REPLICATION` (7), `TYPE_AFTER_CHANGE_REPLICATION` (8), `TYPE_BEFORE_DELETE_REPLICATION` (9) (`ModelValidator.java:38-52`; `PO.java:2785-2787`, `:4300`) — and keeps the received key instead of renumbering (`PO.java:3530-3535`). A listener can even be pure dictionary data: `AD_Table_ScriptValidator` with the events *Table After New Replication / After Change Replication / Before Delete Replication* (`ModelValidator.java:63-65`) bound to an `AD_Rule`.
So the processor chain is: the station's order lines ARRIVE → the processor's core saves them as a replica → a **core listener on `AFTER_NEW_REPLICATION`** (of the declaration table, e.g. `I_Order`) runs Import Orders → Complete ONCE → the replenishment movement is saved locally → the plugin carries it DOWN. The plugin never knows a process exists. Better than a scheduler: immediate, offline, no polling.
**Why the REPLICATION timing is essential, not a detail:** the station's OWN save of its order lines fires the normal `AFTER_NEW`; only the processor's save of a RECEIVED line fires `AFTER_NEW_REPLICATION`. A chain hung on the normal `AFTER_NEW` would run on the station too = a second DocAction executor (FL-8 forbidden, ghost documents). The replication timing is what makes "trigger locally" safe.
**Where the listener lives:** in the CORE — an `AD_Table_ScriptValidator` + `AD_Rule` row (data), or a model validator contributed by a BUSINESS module (a "POS processor" plugin) — **never in the Team plugin**.
**Twin gaps this exposes (measured):** (1) `erp/ad_modelval.js` has no `*_REPLICATION` timings (0 hits; its TIMINGS list :27-28 stops at the normal ones) · (2) the seed has no `AD_Table_ScriptValidator` table and nothing reads it · (3) **the projection bypasses the core entirely** — `crud_overlay.js` `rebuildSide` (T3) rewrites the kernel rows (`DELETE FROM kernel_ops` + `replayRowsInto` + `sealChain`), no `ML.save`, so today NO listener of any kind fires on a received row. A `saveReplica` path in the core (ML.save with `isReplication`, firing the three timings, keeping the received key / uu) is the seam that makes the local trigger possible.
### §9.2 What CAN be separated (all of it, given the seams)
DocAction access (→ access rows, §8 A2) · document numbers (→ core, A3) · core messages (→ core display, A4) · access decisions (→ the core's MRole port, A5) · document authoring and completing (→ core Import Orders on a replica listener, §9.1) · group atomicity (the core tags the commit group, `params.grp`, the plugin keeps it whole) · identity mapping between devices (uu ↔ local key — legacy does this inside its replication plugin too, `ImportHelper` lookups).
### §9.3 What CANNOT be purely separated — the irreducible boundary (three items)
1. **Is a received fact valid HERE?** The plugin's admission is deterministic only over SHARED state (signatures, roster, plan, policy, base hash). The core's save can still refuse a replica for LOCAL reasons — a unique index (`c_order_documentno`, §38.8 B0), a stock or sequence state, a local-only row it points at. Then one device has the fact and another does not. This cannot be pushed into either side alone: the plugin must not run core validation, and the core cannot see the other devices. Legacy has the same edge (an import error is logged per processor). **Handling, not removal:** admission decides on shared data only; a core refusal of a replica becomes a recorded, visible local exception (twin of the import log), the op stays in the log, and a witness compares the devices (FL-6 ghost test).
2. **Two people change the same field before they visit.** Legacy refuses the stale save at the moment of saving (optimistic lock on one server). Here the two saves happen on different devices, so the decision "who wins / hold the agreed value" can only be taken later, at fold time, by the plugin (§4 C2, §13.7). The core only SHOWS it (its own `CurrentRecordModified`, A4). The decision is comm; the look is core — it cannot move into the core.
3. **Which ops belong to one document action.** To keep a Complete all-or-nothing the plugin must treat its result rows as one group. It needs the core to TAG the group (it does — `grp`); the plugin must still know that a tagged group is indivisible. Thin and generic, but it is the one piece of document awareness the plugin keeps.
Everything else in today's Team code is separable; §8.3 A2–A4 are the three places it currently crosses, each with a data-only fix.

## §10 Triggers in legacy — listeners or events? and the more elegant form for the SQLite twin (owner, 2026-10-27: *"In legacy document triggers use listeners or event validators? Study and recommend more elegant way for our SQLite twin."*)
### §10.1 Legacy: BOTH, through ONE dispatcher (EXTRACTED)
`ModelValidationEngine.fireModelChange(po, changeType)` (`org.adempiere.base/.../model/ModelValidationEngine.java:387`) runs, in this order, stopping at the first error: **(1)** `ModelValidator` classes registered for the table on every client (`m_modelChangeListeners.get(table + "*")`, from `AD_ModelValidator` / entity-type classes) · **(2)** those registered for this client (`table + AD_Client_ID`) · **(3)** **`AD_Table_ScriptValidator`** rows — dictionary data bound to an `AD_Rule` script (`MTableScriptValidator.getModelValidatorRules`) · **(4)** an **OSGi event**: `EventManager.newEvent(ModelValidator.tableEventTopics[changeType], …)` then `sendEvent` (synchronous); every handler's error is collected (`IEventManager.EVENT_ERROR_MESSAGES`) and joined. `fireDocValidate` does the same for documents (`documentEventTopics`).
- **Topics** (`org/adempiere/base/event/IEventTopics.java:24-74`): `adempiere/po/` beforeNew · afterNew · **afterNewReplication** · beforeChange · afterChange · **afterChangeReplication** · beforeDelete · afterDelete · **beforeDeleteReplication** · **postCreate · postUpdate · postDelete**; `adempiere/doc/` before/after Prepare · Complete · Void · Close · ReActivate · ReverseCorrect · ReverseAccrual · Post.
- **post* events are different in kind:** sent with `postEvent` (asynchronous) only after a SUCCESSFUL save (`PO.java:2799-2804`, delete `:4544`) — they cannot veto and cannot take part in the save; pure observers.
- **Three ways to subscribe:** the old `ModelValidator` interface (`initialize` → `addModelChange` / `addDocValidate`) · `AbstractEventHandler` (`registerTableEvent(topic, table)`, `doHandleEvent`, `addErrorMessage` — `AbstractEventHandler.java:86-185`) · the newest, **annotations** on a delegate class: `@BeforeNew @AfterNew @AfterNewReplication @AfterChange … @PostCreate @PostUpdate @PostDelete` and `@BeforeComplete @AfterComplete … @AfterPost` (`org/adempiere/base/event/annotations/po/*`, `/doc/*`). Replication itself used the old interface (`ExportModelValidator`, §0).
### §10.2 The twin today (measured, bim-ootb main)
`erp/ad_modelval.js` (855 lines) is ONE form only: `REGISTRY[table][timing] = [{name, fn}]`, `registerValidator(table, timing, name, fn)` (:34), `fireHooks(timing, info, ctx)` — first error aborts (= legacy step 1). **Missing vs legacy:** client-specific listeners (step 2) · `AD_Table_ScriptValidator` data listeners (step 3; the table is not in the seed) · the event bus with topics and collected errors (step 4) · the three `*Replication` timings · the asynchronous `post*` observers. **Also found:** ad_modelval hosts PORTS OF MODEL-CLASS LOGIC as validators (`installMOrderSaveHooks` :64, `installMInOutSaveHooks` :256, `installMInvoiceSaveHooks` :325, `installMPaymentSaveHooks` :434, `installMMovementSaveHooks` :526, `installMJournalSaveHooks` :558 …) while `model_layer.js` also runs `M.beforeSave` (:316). In legacy `MOrder.beforeSave` is the model class's OWN method, not an external validator — two homes for one responsibility (AD-LAYER LAW 5); to be measured whether both fire for the same table, not assumed.
### §10.3 Recommendation — ONE topic bus, legacy's topic names, every subscription form an adapter onto it
1. **The bus.** `ad_modelval.js` becomes a topic bus keyed by the legacy topic strings (`adempiere/po/afterNew`, `adempiere/doc/afterComplete`, `…/afterNewReplication`, `…/postCreate`) with a table filter — the OSGi Event Admin shape, legacy's newest and most general form. The dispatcher keeps legacy's ORDER exactly (§10.1: global validators → client validators → script validators → event handlers; validators stop at the first error, handlers' errors are collected and joined) — so behaviour stays twin.
2. **Adapters, no new semantics.** `registerValidator(table, timing, name, fn)` stays as it is (it maps its TIMING to a topic) → **every existing caller and hook is untouched** · `subscribe(topic, table, fn)` = `AbstractEventHandler.registerTableEvent` · `AD_Table_ScriptValidator` rows → subscriptions created from DATA (port the table into the base via the self-heal patch; the script body = an `AD_Rule` the twin already runs, or a reference to a ported/plugin function) · plugins subscribe through `ctx.events.subscribe` with owner scope, undone on stop (`plugin_registry.js buildCtx`, §2).
3. **Two classes of topic, enforced:** *gate* topics (before*/after* — synchronous, may veto or write in the save's own op group) and *observe* topics (post* + the replica timings for receivers — delivered AFTER the op group has committed, read-only, cannot veto). In the twin "after the group committed" is deterministic and exact (`commitGroup` succeeded) — a strictly better-defined moment than legacy's asynchronous post (noted as an interpretation, not a divergence a user can see).
4. **Why this is the elegant answer for us, not only tidier:** (a) **Separation of concern becomes a CAPABILITY, not a promise** — the Team plugin is granted only *observe* topics + the core's `saveReplica` (§9.1), never *gate* topics; by construction it cannot block, alter or run a document action. W-TEAM-NO-CORE (§8.4) then checks the grant, not grep. (b) **The commit-group seam (§4 T2) disappears into the bus** — `postCreate/postUpdate/postDelete` delivered once per committed group IS the after-commit observer the plugin needs; `crud_overlay.js _teamPush` (T2) is deleted. (c) **The POS chain is a row:** an `AD_Table_ScriptValidator` on `I_Order` · *After New Replication* → the Import Orders process (§9.1) — no code in any plugin, visible in the dictionary like any legacy site's configuration. (d) **The model-class hooks go home:** M*.beforeSave/afterSave/completeIt live in `model_layer.js` (the PO's own methods, called by the save), the bus carries only EXTERNAL listeners — the double home in §10.2 is removed (deletion budget).
5. **Witnesses (spec before code):** W-BUS-ORDER — for one table, a global validator, a client validator, a script-validator row and two handlers fire in legacy order; a validator error stops the rest; two handler errors come back joined · W-BUS-REPLICA — a `saveReplica` fires `afterNewReplication`, NOT `afterNew` (and a station's own save the reverse) — the FL-8 safety of §9.1 · W-BUS-OBSERVE — an observe subscriber cannot veto (its throw is logged, the save stands) and is called once per committed group, never for a rolled-back one · W-BUS-COMPAT — every existing `registerValidator` hook produces the identical outcome (X of N over the tables that have hooks today) · W-BUS-ROW — a script-validator ROW triggers a process on a replica save with no code change.

The POS processor chain (G-1…G-3) becomes a script-validator row on top.
