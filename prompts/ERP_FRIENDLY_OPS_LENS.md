## 1. Rules this spec lives under (no new ones invented)
- **TWIN CARDINAL RULE (CLAUDE.md):** the default SQLite ERP stays equal to legacy iDempiere, L&F included. A friendlier operation is therefore a **lens the user switches on**, never a change to the default screens or results. The parallel run (`scripts/bridge/run_all.sh`) must stay green with the lens OFF, and the lens ON must produce the **same books** (same documents, same posting) by fewer or easier gestures.
- **Licence (README / `erp/lens/odoo/README.md`):** Odoo CE is LGPL-3.0, ERPNext GPL-3.0; both are incompatible with GPLv2-only. We observe behaviour (run it, record the gestures and executed rows) and write our own code. No Odoo/ERPNext source, schema or templates copied into `erp/`. Odoo Enterprise: never.
- **Primal law:** the user's eyes are never the test instrument. Friendliness is measured as numbers (gestures, screens, fields typed, errors), asserted by a witness.

## 2. What "friendlier" means here (measurable)
For one business flow F and one actor: **G(F)** = count of discrete gestures (click, key chord, typed field) from a fresh window to the finished, posted result; **S(F)** = screens/windows opened; **M(F)** = mandatory fields the user must fill that the system could have defaulted; **R(F)** = places the user must remember a number from one screen to type on another.
A lens op qualifies when it lowers at least one of G/S/M/R for the same final books (diff = 0 on `fact_acct` and stock) and breaks none of the others.

## 3. Method (per flow)
1. Pick the flow. First set: (a) sales order → ship → invoice → pay, (b) purchase → receive → vendor bill, (c) manufacturing order → issue → receive (the Libero film flow, 43 clicks measured on the twin: `erp/tests/film_mfg_intro.js`, `§ERP_FILM_CURSOR clicks=43`).

3. Run the same flow on a throwaway Odoo 17 (docker `odoo` + `odoo-db`, local only) with Playwright, recording the same four numbers and the executed rows (document states, stock moves, journal items) as a static oracle (`out/odoo_<flow>.json`). ERPNext second, same shape.
4. List every place Odoo needs fewer gestures. Each becomes a named candidate `FO-n` with: what it does (behaviour only), which twin verb already exists, what is missing.
5. Implement each accepted candidate once in the generic AD layer (AD-LAYER LAW: no per-window code), behind the lens switch. Witness RED then GREEN: (i) lens OFF == legacy, (ii) lens ON books == lens OFF books, (iii) G/S/M/R strictly lower.

## 8. Integrity contract for lens operations (owner directive 2026-10-15)
> *"our .save() equivalent must have same overriding doc event rules. All in respective layers for similar ease of maintenance. ... happening only in own Kernel ERP lane ... unless we can also likewise setup same sequence of events. That be solid ground to report model integrity on."*
1. **One write path.** A lens op never writes a table itself. Every record it creates or changes goes through the twin's `.save()` (`erp/model_layer.js`: model `beforeSave` -> `BEFORE_NEW|BEFORE_CHANGE` validators -> write -> model `afterSave` -> `AFTER_NEW|AFTER_CHANGE`, lines ~296-302, 484-493) and every document state change through the doc-action engine (`erp/ad_docfsm.js` plus the model's `docActions`). The event rules live in those layers only, never in the lens, so there is one place to maintain.
2. **Layers.** UI lens (what the user sees and clicks) -> generic AD layer (callouts, defaults, access) -> model layer (`.save()` and events) -> doc layer (doc-action FSM) -> kernel op-log. A lens module may call downward only through each layer's public entry point. A lens needing a new rule adds it to the layer that owns it (AD-LAYER LAW), not to the lens.
3. **Scope.** Lens ops exist only in the Kernel ERP lane. Legacy iDempiere is unchanged and has no lens. The integrity claim therefore compares the twin's event sequence for a lens gesture with the sequence legacy produces for the equivalent plain gestures.
4. **The report = event-sequence equality (`§EVENT_SEQ`).** Add one ordered trace line per fired event at the two existing choke points (`fire()` in `model_layer.js`, the doc-action dispatcher): `§EVENT_SEQ op=<n> table=<t> id=<k> event=<BEFORE_NEW|AFTER_SAVE|DOCACTION:CO|...>`. Witness, per lens op: (a) the sequence from the lens gesture equals the sequence from the equivalent un-lensed gestures, event for event, in order; (b) wherever the legacy pilot can run the same business step (`scripts/pilot`, WS types), its model-event order is read once and the twin's must equal it; where legacy cannot be driven, the claim is labelled "twin-internal" and not "legacy-equal". (c) `fact_acct`, stock and document numbers equal. Verdict prints `INCONCLUSIVE`, never PASS, if the sequence was empty or a table was not exercised.
5. **What is reported.** Per candidate FO-n: gestures before/after, `§EVENT_SEQ` equal Y/N (count of events compared), books equal Y/N, legacy-checked Y/N. Model integrity is claimed only on the rows where all are Y.

## 11. Libero Issue/Receipt: bend toward Odoo, or auto-complete the documents? (2026-10-15, read of pshepetko/org.idempiere.mfg @ b2adfea0)
**Facts (file:line into the Libero source, GPLv2):**
- `MPPCostCollector.createCollector` (:73-156) builds a collector AND completes it (`setDocAction(CO)`, `saveEx`, `processIt(CO)` at :150-155). So in legacy every collector is auto-completed the moment code creates it; only the Cost Collector WINDOW makes the user complete each by hand.
- `MPPOrder.createIssue` (:1256-1330) loops the component's storage lines (FIFO/LIFO order from `getStorages`) and creates ONE collector per storage line: one component can yield several collectors. It chooses the collector type itself: ComponentIssue, MethodChangeVariance (BOM line with QtyBatch=0 and QtyBOM=0) or MixVariance (co-product). `forceIssue` issues the rest from the line's own locator.
- `MPPOrder.createReceipt` (:1190-1245) creates one MaterialReceipt collector, then sets DateDelivered, DateStart, and DateFinish when delivered+scrap >= ordered, and saves the order.
- The legacy one-step already exists: the form `org.libero.form.OrderReceiptIssue` / `WOrderReceiptIssue` with a Delivery Rule (Backflush | Only Issue | Only Receipt), a component grid with QtyToDeliver / QtyDelivered / QtyScrap, an on-hand check, then `createIssue` per selected row and `createReceipt`. red1's later InfoWindow port (`org.libero.infowindow.OrderReceiptIssue`) wires issue only; the receipt is embargoed "until InfoWindow can accept row level data input".
- The twin has `collectorFields` (the field population of createCollector) and the collector DocAction (libero_cost.mjs), but NOT `createCollector`'s save+complete, `MPPOrder.createIssue/createReceipt/getStorages`, nor the form. That absence is why the twin feels crude.
**Decision (no Odoo bending needed):** port `createCollector` (create + complete), `getStorages`, `createIssue`, `createReceipt` and the Backflush form/process faithfully, in the libero_* GPL chunks, and give the order a one-click Backflush that opens that form with defaults (QtyToDeliver = open quantity, on-hand checked). It is legacy behaviour exposed through one gesture, so the twin rule holds and the event sequence per collector equals the window path.
**Rejected: Odoo's backorder split.** It would change order identity, pp_mrp supply/demand rows, the PP_Order_Cost snapshot, document numbers and DateFinish logic, so lens-on books and sequences would differ from legacy.
**Impact map of the faithful port:** storage (M_Transaction + storage lines per collector), CostEngine details and rate variances (already ported), order quantities and dates, pp_mrp, Manufacturing Output dashboard goal, and M6 postings (Doc_PPCostCollector per collector: unchanged unit of posting). All writes go through `.save()`/docAction, so `§EVENT_SEQ` applies: the Backflush path must equal N plain collector completions, in order. One atomic group: any collector refused rolls the whole backflush back (the twin's op-group seal; legacy shares one transaction).

### 20.A Slice A spec: the Pack In engine (`erp/pipo_packin.js`), ported from org.adempiere.pipo2 (read 2026-10-16)
- **Read:** a 2Pack zip -> its `*/dict/PackOut.xml` (zip central directory + `DecompressionStream('deflate-raw')`, no library). Root `<idempiere Name Version UpdateDictionary Client>`: UpdateDictionary="true" -> update mode Y (PackInHandler.java:120-127); Client "0-..." needs the System context, a tenant pack needs a tenant (:129-136) - the twin applies a System pack in System context (AD_Client_ID 0) regardless of who is logged in, as Incremental2PackActivator does at server start.
- **Elements** (PackInHandler.java:258-276): a child element WITHOUT a `type` attribute is a PROPERTY (a column value) of its parent; one WITH a type (`table`, `translation`, `custom`...) is a CHILD record. Processing is depth-first: the element, then its children (:278-311). Unresolved -> deferred and retried at the end.
- **Handlers:** `SQLStatement` (type custom) -> SQLStatementElementHandler; any table -> GenericPOElementHandler (GenericPOElementHandler.java:75-123). ## 26. Slice D spec: a declarative manifest generates the bundle's 2Pack (2026-10-17, session 4, owner-agreed order §13)
Goal (§20.4): a bundle DECLARES the dictionary rows it provides; one engine writes them out as a real `2Pack_<version>.zip`, once, at development time; from then on the bundle carries that pack like any legacy plugin (Pack In at Start, Packages Installed, Pack Out to redeploy). Not a lens op and not a runtime path: nothing persistent is written by generation.
**Facts read first (not assumed):** `pipo_packout.js` already writes the legacy format (W-PACKOUT O1: 1,077/1,143 properties == Libero's legacy XML, 0 exporter defects); `exportPackage(q, header, details)` takes detail lines P/X/D/DS/SQL/ET/MSG; a non-official `<Table>_ID` (> 999999) is never written, references to non-official rows go by UU (ReferenceUtils.getTableReference). `model_layer.newPO` stamps no AD_Column.DefaultValue (Java X_ ctors are commented out; DefaultValue comes from GridTab.dataNew / GridField.getDefault, a window path); physical defaults come from `ad_ddl_default` at insert. Libero's `2Pack_1.0.3.zip` was written by hand (§22 B6) - it is the oracle for the generator.
**Declaration (generic, no per-kind code, AD-LAYER LAW):** `manifest.provides = { version, date, description, updateDictionary, elements: [ { key, table, uu?, values: {...} } ] }`. A value is a literal, an official id, `{ ref: '<key>' }` (another declared element) or `{ table, uu }` (an existing dictionary row). `table` decides the Pack Out line: AD_Process -> P (its declared AD_Process_Para children are written inside it by the P handler), AD_Form -> X, AD_EntityType -> ET, AD_Message -> MSG, `SQLStatement` -> SQL (values.statement, values.dbType), any other table -> D with `SELECT * FROM <T> WHERE <T>_UU='<uu>'`.
**Engine `erp/pipo_packgen.js` (`PipoPackGen.generate(db, manifest)`), on the dictionary DB inside `SAVEPOINT packgen`, always `ROLLBACK TO` at the end:**
1. UU: the declared `uu`, else a name-based UUID v5 (RFC 4122, SHA-1) of `<manifest.id>/<table>/<key>` - stable per bundle + element, so a regeneration finds the same rows.
2. Row = declared values -> refs resolved (`{table,uu}` absent -> refused naming it) -> AD_Column.DefaultValue where it is a context-free constant (`Y`/`N`/a number/a quoted literal; an `@...@` or SQL default is skipped and counted `§PACKGEN default-skipped`) -> `ad_ddl_default` -> standard columns (AD_Client_ID 0, AD_Org_ID 0, IsActive Y, Created/Updated = provides.date, CreatedBy/UpdatedBy 100). Id = MAX(MAX(id), 999999)+1 inside the savepoint (customization range; never exported, L4).
3. Mandatory check (PO.save would refuse): every active, non-virtual AD_Column IsMandatory='Y' must be non-null, else refused naming `table.column`; unknown table refused.
4. `PipoPackOut.exportPackage` with header Name=manifest.id, PK_Version=provides.version, IsExportDictionaryEntity = updateDictionary, Created/Updated = provides.date -> zip (`packageZip`). Log `§PACKGEN bundle= version= elements= records= bytes= defaultsSkipped= ms=`.
5. CLI `erp/tools/gen_2pack.js <bundle.mjs>` (headless page, same harness as the witnesses) writes `<bundle dir>/<packsDir>/2Pack_<version>.zip`; an existing file with different bytes is REFUSED (a released pack is immutable - bump the version, Incremental2PackActivator); identical bytes -> `unchanged`.
