# Prior art covers scriptor's parts, not the whole

**To our knowledge, we found no system, paper or patent that combines both halves of the design: a serverless compiler that turns a schema, roles and topology into signed per-device publish/fetch plans, and a signed catalog of parameterised queries that data holders answer later, under their own access check, with an "as of" stamp, over a passive store-and-forward carrier.** No item we rated "exact", and the research had real limits (see the search-depth section). Each half has a close ancestor. For the planner, the nearest is SQL Server merge replication, which derives join filters from foreign-key relationships but runs on a central Publisher, is not signed, and has no pre-rollout simulation ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/replication/publish/automatically-generate-join-filters-between-merge-articles)). For the deferred query, the nearest is MIT's CarTel/ICEDB, which runs a SQL query with a `RATE` clause on intermittently connected nodes and delivers results at the next contact, but through a central portal that issues the queries and receives the results ([CarTel](https://people.csail.mit.edu/hari/papers/p92.pdf)). Astrolabe supplies signed, expiring, issuer-gated query code with no central server, but over gossiping live agents ([Astrolabe](https://www.cs.cornell.edu/projects/quicksilver/public_pdfs/astrolabe.pdf)). The user's hypothesis, that the missing enterprise local-first piece is a replication-strategy generator, is supported for the local-first engine world, where every engine we read has a developer hand-write the sync scope. It is overstated for enterprise software as a whole, where profile and filter tools already exist. The claim that cheap AI-assisted coding makes it feasible is untested by anything we found. The scriptor also does not close the authority gap (arbitration of scarce resources, forks, restore rollback, legal position) identified in the earlier serverless-transactions precedent report, and the novelty claim should be worded accordingly, as set out in the last sections.

## The planner half: scope is hand-written everywhere except one central ancestor

In every modern sync engine whose documentation we read, the unit of partial replication is an artefact a developer writes. Zero syncs "the union of all active queries' results" from queries in app code ([Zero queries](https://zero.rocicorp.dev/docs/queries)). Electric defines a shape as a table plus an optional `where`, set by the server or proxy, and shapes cover a single table, so related data needs further shapes ([Electric shapes](https://electric.ax/docs/guides/shapes)). PowerSync stream queries must select related rows explicitly through subqueries ([PowerSync Sync Streams](https://docs.powersync.com/sync/streams/queries)). Couchbase routes documents to channels through a hand-written JavaScript sync function ([Couchbase](https://docs.couchbase.com/sync-gateway/current/sync-function-api.html)). Ditto devices declare subscription queries, and for multi-hop relay every intermediate device must subscribe to the same data ([Ditto](https://docs.ditto.live/best-practices/sync-handling)). Closure is a documented footgun rather than a checked property: Realm showed linked objects as nil unless subscribed, Zero returns an `unknown` result type for possibly incomplete data, and PowerSync's own migration guide says moving from Electric "will most likely not be 1-for-1; partial sync will likely need to be redesigned" ([PowerSync migration](https://docs.powersync.com/migration-guides/electric)). That last source is a competitor's guide, so treat it as vendor-biased. These products are all still server-centred except Ditto's mesh and the capability-based peer systems.

The one ancestor that derives scope from schema structure is SQL Server merge replication. The administrator writes a parameterised row filter on a root table, and "replication can generate the filters automatically based on the foreign key to primary key relationships" for the dependent tables ([auto-generated join filters](https://learn.microsoft.com/en-us/sql/relational-databases/replication/publish/automatically-generate-join-filters-between-merge-articles)). The filter is parameterised by subscriber identity, using `SUSER_SNAME()` or `HOST_NAME()`, and Microsoft documents that `HOST_NAME()` can be overridden and so must not be used for access control ([parameterised filters](https://learn.microsoft.com/en-us/sql/relational-databases/replication/merge/parameterized-filters-parameterized-row-filters)). The same page records a closure gap: with non-overlapping partitions, a parent row inserted late is downloaded but its already-existing child rows are not. A mis-declared partition option can cause non-convergence. This is the most important finding for the planner, because it shows both that FK-derived scope is old, and that closure correctness was left to the DBA with no pre-rollout check. Merge replication needs a central Publisher/Distributor, derives scope from identity only (no role or topology model), and emits no signed per-device plans. MEGA HOPEX's "reduced synchronization" also extends scope along foreign-key links, but we saw only a search snippet of it ([MEGA](https://doc.mega.com/hopex-v4-en/INFA/Synchronization.Reduced_Synchronization_Strategies_(Logical__3e_Ph.html)). Dynamics 365 offline profiles let administrators set per-table sync intervals and filters (all, related, custom) with the cloud as aggregation point ([Microsoft Learn](https://learn.microsoft.com/de-ch/dynamics365/field-service/mobile/offline-data-sync)).

We found nothing that does the simulation-based closure and leakage check on a replication plan before rollout. The adjacent items are formal but sit elsewhere. Blockaid checks each query against SQL-view policies using query determinacy and SMT solvers, but online, at a proxy ([Blockaid](https://arxiv.org/pdf/2205.06911)). A 2026 preprint verifies local-first access control structures in Rust/Verus ([arXiv 2604.23560](https://arxiv.org/abs/2604.23560)). Electric's reported Antithesis testing is of the engine, not of a deployment's plan ([Electric 1.0](https://electric.ax/blog/2025/03/17/electricsql-1.0-released.md)). The placement literature optimises fragment allocation given a workload (ILP, hypergraph, community discovery) and does not take roles or a dictionary as input, as far as the snippets showed ([Liu et al., TPDS](https://www.comm.utoronto.ca/~jrwang/file/TPDS20.pdf)). Two patents are the nearest on the generation side: MarkLogic's query-defined replication subsets for field devices, with queries hand-written and a server as master (abandoned, [US20140304293A1](https://patents.google.com/patent/US20140304293)), and SAP's generation of an offline application from an application model with a per-user subscription (abandoned, [US20090024645A1](https://patents.google.com/patent/US20090024645)). Our inference is that the scriptor's differentiators on this half are the combination of role-and-topology input, signed per-device output, and a plan-level simulation check with no server, not FK-derived scope on its own.

## The deferred-query half: close ancestors differ on control plane, trust and as-of

The reply-schedule idea has direct lineage. TinyDB's grammar has `SAMPLE PERIOD`, `FOR`, `STOP ON EVENT` and `ONCE`, with queries pushed to the node holding the data and tuples stamped with production time and, for aggregates, an epoch number ([TinyDB TODS](https://courses.cs.duke.edu/spring07/cps296.1/papers/tods05-MaddenFranklinEtAl-tinydb.pdf)). It has no "report on change" clause and no calendar clause such as end of day. We found no security discussion in the extracted text, and the only issuer is the basestation. CarTel/ICEDB extended this to intermittent connectivity: `RATE 5 mins` batches are "delivered whenever the car is next able to send data to the portal", over CafNet, a delay-tolerant stack that includes mule carriage ([CarTel](https://people.csail.mit.edu/hari/papers/p92.pdf)). Lindner and Madden's 2004 position paper already claimed, "to the best of our knowledge", that nobody had augmented a query processor for disconnection ([Lindner & Madden](https://people.csail.mit.edu/wolfgang/papers/GI-WSN04.pdf)), and CarTel frames its work as "extending the notion of continuous queries to handle intermittent connectivity". That is a warning for any novelty claim: the idea of a scheduled query answered by the data holder at its next contact is two decades old.

What separates the design from the MIT lineage is specific, and each point is a reading of what we extracted rather than a claim about every MIT paper. On the control plane, CarTel's portal "is the point of control and configuration" and "the 'sink' for all data", and applications issue queries through ICEDB's API and results are not sent to the querying application directly; they populate the portal's database. In the design, any authorised device can address a signed request to a peer, and there is no sink. On trust, CarTel has portal user authentication, with users seeing only data from nodes they host, and a footnote that a public-key-derived identifier "would ease message authentication"; we found no result signing in the text read, and TinyDB shows none. In the design, both the catalog and each reply are signed. On as-of semantics, CarTel acquires readings when the clock is divisible by the `RATE` against GPS-synchronised clocks and tuples carry their `time`; TinyDB assumes a synchronised epoch. In the design, the responder attests the state of its own store as of a stamp, with no shared clock assumed. We did not read the ICEDB thesis beyond its abstract ([DSpace](https://dspace.mit.edu/handle/1721.1/43064)), so a more detailed claim about ICEDB timestamps or identity would need that read first. Chandar and Athalye's slides come closest to the "no central server, DTN, SQL-like queries" combination, with deadlines and "Best"/"Fast" completion rules, but we saw only a slide-deck summary with no venue or year, and it showed no schedule clause or signing ([slides](https://www.slideshare.net/slideshow/distributeddatabasesforchallengednet/12728671)).

The authority and signing ancestors come from different families. Astrolabe is the closest on trust: aggregation function certificates are "signed and timestamped", installed only if issued by an ancestor zone or by a client whose certificate grants propagation, expire unless renewed, and MIB certificates are signed to prevent "false gossip" ([Astrolabe](https://www.cs.cornell.edu/projects/quicksilver/public_pdfs/astrolabe.pdf)). Its limits relative to the design are exact: queries are free-form restricted SQL, not a catalog of named parameterised queries; they run over small gossiped attribute tables, with only an `&odbc:` path touching local sources and no holder-side access check described in the excerpt read; results are replicated zone aggregates, not answers to one requester; the agents are always running and gossip over UDP/HTTP; and the aggregate's `issued` time is its computation time, which the paper itself says ignores when the leaf attributes were updated. Astrolabe also admits two relevant weaknesses: certificates "cannot be easily revoked until they expire", and authorised agents can lie about attribute values. Our inference is that a signed reply proves attribution, not truth, and that revocation of a signed catalog entry will need a stated design answer. ORCHESTRA is the closest on schedule and autonomy: each peer's administrator publishes and reconciles "as often as it wants", with no central server and a DHT-based update store. What travels is edit logs, not query requests, and its overview paper showed no signature mechanism ([ORCHESTRA, SIGMOD Record 2008](https://www.cs.ucdavis.edu/~green/papers/sigrec08.pdf)). Its Q subsystem saves parameterised view templates, which is the nearest analogue to registered parameterised queries in the academic set.

The "registered parameterised query" element is the most widely known single piece, and the notes under-searched it. Rocicorp Zero's clients do not send arbitrary queries: they send a named query with arguments that the server resolves to ZQL, applying permissions in the endpoint ([Zero auth](https://zero.rocicorp.dev/docs/auth); Zero architecture came from a search snippet and a third-party mirror). That is a catalog of parameterised queries, but server-resolved and central. Stored procedures, GraphQL persisted queries and signed stored procedures were on the researchers' unchecked list. Our inference is that "a catalog of vetted parameterised queries" cannot be claimed as new; the claim has to be the signed catalog bound to holder-side execution and signed, stamped replies over a mailbox. For the holder-side check, Willow's Meadowcap read capabilities are "enforced sender-side" for sync ([Willow](https://willowprotocol.org/specs/sync/index.html)), and Keyhive/Beelay syncs "everything which each side thinks the other has access to" with signed messages ([Ink & Switch](https://www.inkandswitch.com/keyhive/notebook/)). Both are document or key-value sync, not named queries. Enterprise anchors for deferral are server-based: Service Broker queues with conversation correlation ([Microsoft Learn](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2005/administrator/ms345108(v=sql.90))), Oracle AQ delay and expiry windows ([Oracle](https://docs.oracle.com/cd/A91202_01/901_doc/appdev.901/a88890/qintro4.htm)), SSRS subscriptions as "a standing request to deliver a report at a specific time or in response to an event" ([Microsoft Learn](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2005/ms155911(v=sql.90))), and Oracle materialized-view `START WITH`/`NEXT` ([Oracle](https://docs.oracle.com/cd/A83908_02/NT816EE/DOC/server.816/a76989/ch4b8.htm)). So the schedule vocabulary (once, periodic, at a time, on event) is not new in itself. The oldest relevant patent we saw, US5253341 (1991, expired), already describes prestored queries with periodic answer packets and overnight forwarding by a concentrator, with no signatures ([Google Patents](https://patents.google.com/patent/US5253341)).

## How thorough the search was, and what moved in 2026

The search was broad but shallow in depth, and it was done with a general web-search tool and a page-fetch tool that returns model-written summaries, not raw text. The planner-side researcher made about 33 tool calls and read almost everything through those summaries, with only the Microsoft Learn merge-replication pages returned near-verbatim. The patent and project researcher ran 25 queries and about ten page fetches, and states that "no exact match" means "none surfaced", not "none exists". The lineage researcher downloaded and read the TinyDB, CarTel, Lindner-Madden and Rover texts and the Astrolabe, SDIMS and ORCHESTRA texts for the gossip question, but several of these were targeted section reads plus keyword sweeps, and the security negatives (no signing in TinyDB, no signing in the ORCHESTRA overview) are keyword-based. Fetches failed or were blocked for PIER, the Piazza and TSIMMIS primaries, the ICEDB thesis PDF and the pome PyPI page.

Several searches were not done at all, so the absence of a closer match is weak evidence. Patent offices were not queried directly: no Espacenet, WIPO PATENTSCOPE or USPTO search, no CPC-class searches (the notes name G06F16/27, G06F16/2455 and H04L67/1095 as the classes to run), no assignee-specific searches (SAP, Microsoft, Salesforce, Couchbase, Ditto, Oracle), and essentially no CN/JP/KR/DE filings. Claim text was missing for the ServiceNow, IBM, VMware and Facebook patents. Several patents that surfaced only as snippets were not fetched, for example US7693832 (user-defined sync filters), US10528541B2 (disconnected local-DB answers) and US12609839 (peer relay to offline devices). The ACM Digital Library, Semantic Scholar and dblp were not queried, and database-community local-first query papers (VLDB, SIGMOD, CIDR) may exist unseen. The researchers' own unchecked lists name systems that are plausible closer prior art: Cimbiosys (per-device filters, topology-independent partial replication), Bayou and Coda hoarding profiles (seen only as snippets and summaries), SymmetricDS, MobiLink, Oracle Database Mobile Server, Couchbase Lite, PouchDB, Nostr relay filters, Named Data Networking signed data, GraphQL persisted queries, signed stored procedures and other query allowlisting, Datomic and Firebase security rules, Secure Scuttlebutt, Hypercore, Solid pods, AT Protocol, Matrix, Data MULEs, ZebraNet and Madden's 2010 survey. Also unchecked were network-verification and simulation tools (Batfish, TLA+ or Quint models of sync, deterministic simulation testing, Jepsen-style work) that could bear on the plan-level simulation claim. Our inference is that Cimbiosys, SymmetricDS and the persisted-query family are the most likely places for a closer hit, the first two for the planner half and the last for the catalog element.

## Wording the claim, and the authority gap the scriptor does not close

A defensible wording, built on the notes' own hedges, is: "To our knowledge, we found no published system, paper or patent that combines (1) a standalone compiler that derives signed per-device publish/fetch plans from an application dictionary, declared role and device needs and topology, with a pre-rollout simulation check for closure and leakage, and (2) deferred queries drawn from a signed catalog of registered parameterised queries, executed by the data holder against its own local database under its own access check and answered later on a declared schedule as a signed result with an 'as of' stamp, carried over a passive store-and-forward transport with no always-on server. Individual elements have close precedent: foreign-key-derived replication filters (SQL Server merge replication), signed authority-gated query code without a central server (Astrolabe), scheduled queries answered by the data-holding node at its next contact (TinyDB, CarTel/ICEDB), and queued request/response over SMTP (Rover). Our search was limited (no direct patent-office or ACM DL search) and we do not claim to be the first." Avoid "first", "novel" without the qualifier, "no prior art exists" and "patentable", which no search here supports. Active patents we saw (ServiceNow US11509729B2, VMware US11755356B2) were not close in the summaries read, but no claim-level or freedom-to-operate analysis was done; that needs a professional search.

The hypothesis needs splitting into three parts. That the local-first engine world lacks a replication-strategy generator is supported: every engine we read has scope hand-written, closure appears as a footgun, and the PowerSync guide says partial sync must be redesigned on migration. The HN threads we saw show partial sync is a recognised pain point, though we read only search summaries of the comments and found nobody framing it as a generated plan or framing cross-node reporting at all ([HN](https://news.ycombinator.com/item?id=45333021)). That it is the missing piece for enterprise as a whole is overstated by inference, because merge replication and Dynamics offline profiles are enterprise precedent of a partial kind. The likelier explanation for the gap in local-first, also an inference, is that server-centred vendors have little reason to build a serverless planner. That cheap AI-assisted coding is what makes it feasible is a claim none of the notes tested or sourced. Our inference is that coding cost is not the binding constraint: the hard parts are the closure semantics that Microsoft documents as an unsolved edge case and the authority questions below, and a deterministic compiler has to be correct, not just written.

The precedent report on serverless transaction systems found that every production system keeps an arbiter: a notary, an orderer, a processor, a git host or a human reconciler, and it left forks, restore rollback, owner re-signing and the Thai legal position open. The scriptor does not change that, and the design should say so. A plan states what to publish and fetch; it does not decide which of two offline devices wins the last unit, because uniqueness, sequential IDs and threshold invariants are among the cases Bailis et al. show need coordination ([Bailis et al.](https://www.alphaxiv.org/abs/1402.2237)). A deferred query is a read at an as-of stamp, so it cannot reserve stock or settle a position; the stamp tells the reader how old the answer is, not that it is still true. A signature proves a holder issued a reply, not that the holder is honest, and Astrolabe's own admitted deficiency and the secure-aggregation literature point the same way. A restored backup can re-issue signed history and a key holder can re-sign it unless a head hash is anchored outside their control ([Holochain source chain](https://developer.holochain.org/concepts/3_source_chain/); the specific scenarios were labelled inferences in the earlier report). Signed plans add one new root of trust, the plan signer, whose revocation inherits the Astrolabe weakness that certificates cannot be revoked until they expire (our inference). Whether Thai pawnshop, accounting or electronic-records law accepts a per-device signed ledger and mailbox-carried queries was not established and needs a Thai lawyer ([Revenue Department](https://rd.go.th/25480.html), as cited in the earlier report).

## Conclusion

The research shifts the novelty question from "has anyone built a replication-strategy generator or a deferred distributed query?" to "has anyone put a signed, serverless control plane around either?" For the planner, the answer we found is that FK-derived scope has existed since SQL Server merge replication, so the new content is role-and-topology input, signed per-device output and a plan-level simulation, and that last piece is the least precedented element in the whole design. For the query half, the useful distinction from the MIT TinyDB-to-ICEDB lineage is not the schedule clause or the data-local execution but the replacement of a portal-as-sink with signed, peer-addressed requests and holder-attested, as-of-stamped replies.

The honest strategic reading is that the design's strongest and weakest points coincide. The simulation check is both the least precedented element and the one most exposed to the merge-replication lesson that closure correctness hides edge cases, so its claims should be framed as bounded by the simulated model rather than as guarantees. The next inexpensive steps are to read the unread primaries that could change the verdict (Cimbiosys, SymmetricDS, the ICEDB thesis, ORCHESTRA's 2007 and 2010 papers), to run a CPC-based patent search, and to carry the fork, rollback and re-signing scenarios into the scriptor's simulation as named test cases rather than leaving them to the arbiter question the earlier report left open.
