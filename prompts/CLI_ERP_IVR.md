## 62. The door's own roster of trusted keys, and taking trust back (2026-11-19, owner "yes" to item 3 of the ONE LEDGER open list; spec before the code)
**Issue:** the page admits a row only if its signature verifies under its own key or a key the owner pinned (§58/§59). The door admits everything: `ledger_sign.parseOps` replays every row of the file, signed or not, by any key, and (§61 limit 5) applies every UNDO/REDO marker. So a forged row, or a row by a key nobody trusted, changes what `red1>` shows while the page ignores it: door ≠ page, and the shared file is only as safe as its weakest reader. Second gap, both ends: a key once trusted cannot be untrusted (no revocation).
**Rule:**
1. **The door's roster** is a file next to the door key: `~/.config/red1/ledger_roster.json` (0600; `$RED1_LEDGER_ROSTER` names another), `{trusted:[{kid, fp, at}], revoked:[{kid, fp, at}]}`. `kid` = the SPKI hex a row's `signed_by` carries; `fp` = the page's fingerprint form (sha256 of the SPKI, 16 hex, dashed), the same string the page's Trust button shows.
2. **Admission at the door = the page's §59 rule, in `parseOps`:** a row counts only if its signature verifies under the door's own key or a trusted roster key (v2 rows over the content hash `sha256('cs2|'+canonicalV2)`, v1 over `op_hash`); no signature, not admitted. A group (`gid`) is admitted whole. Markers (§61) count only if admitted. Bare legacy lines (from before the door signed) stay as today: the door's own, sealed on its next append. A row not admitted is left out of the replay, never removed from the file. stderr: `§LEDGER excluded rows=<n> why={...}` and, per unknown key, `§LEDGER unpinned key fp=<fp> rows=<n> (trust it: node common/door/ledger_sign.js trust <fp>)`.
3. **Commands** (`node common/door/ledger_sign.js …`): `keys [<opfile>]` lists every key that signed rows in the file: fp, rows, and `this door` / `trusted` / `revoked` / `unknown`, plus this door's fp; `trust <fp> [<opfile>]` finds the key with that fingerprint in the file and adds it (a revoked key comes off the revoked list); `untrust <fp>` moves it to revoked. With no `<opfile>`: `$BIM_OBJECT_OPLOG`, else the door's default log.
4. **Revocation means the key's rows stop counting, all of them** (past ones too), on both ends, the same as an unknown key. There is no trusted clock in the file, so "rows before the revocation stay" cannot be proven; stated, not built. Rows that depend on them (lines of an order the revoked key created) then point at a missing record: that is the visible cost of revoking.
5. **The page:** a "Keys" button beside the pill (when a folder is attached) opens a small panel: **this browser's own fingerprint** (what the owner compares with `ledger_sign.js keys` before `trust` at the door), and each trusted key with an "Untrust" button. `__crud.ledgerUnpin(kid)` takes it off the roster, re-reads the file, and the roster is saved. Nothing else on the page changes.
6. **Cost:** one ECDSA verify per row on every door run (Node's sync verify); measured in the witness for the file it builds, not extrapolated. A lost or replaced door key makes the door's own OLD rows unknown: the same `unpinned` line names them and `trust` brings them back.

## 61. Undo and the History scrub in ledger-file mode: an undo is a NEW row (2026-11-19, owner "Proceed one ledger"; item 2 of the ONE LEDGER open list; spec before the code)
**Issue (§55 rule 5, §59 rule 5):** with a ledger folder attached, scrubbing History back past a document action (`crudFoldBack`) or forward again (`crudFoldForward`) does nothing but log `§LEDGER unsupported`. Undo today flips `undone` on an EXISTING row and re-appends a snapshot of that same id (`crud_overlay.js` `foldBackDocOp`, `kernel_ops.js` `undoOp`/`redoOp`). The shared file only grows, is chained, and the door numbers its next row from the file's last id, so a repeated id would fork the chain or collide. Redo was refused for a second reason: it re-admits the earliest `undone=1` row, and §59 marks rows it does not trust `undone=1` too, so redo would bring an untrusted row back.
**Rule (file mode only; IndexedDB mode is unchanged):**
1. **Undo writes one new row** `op_type='UNDO'`, parameters `{op_type:'UNDO', targets:[op_uuid, ...]}`: the rows of the tip gesture, the same rows `CORE.foldBackGroup` picks today (a group whole). It is committed with `K.commitGroup` inside `_withFreshSide` (file lock, fresh read), sealed, signed and appended like any commit. **Redo** writes `op_type='REDO'` with the rows `CORE.foldForwardGroup` picks (the earliest undone gesture). Nothing to undo or redo: no row.
2. **ONE rule for reading them, shared by page and door:** `KernelOps.foldMarkers(rows)` (pure): walk the rows in id order; an `UNDO` takes its targets out, a `REDO` puts them back; returns the op_uuids that end undone. The page applies it on every hydrate from the file (`undone=1` in memory only, never written); the door applies it in `ledger_sign.parseOps`, so `red1>` replays exactly what the page shows.
3. **Only admitted markers count** (§59): an `UNDO`/`REDO` row signed by an unpinned or forged key is not applied. **Untrusted is not undone:** §59's excluded rows become `undone=2` (every fold reads `undone=0`, so no window changes), redo reads `undone=1` only, so it can never bring an excluded row back. The fold-forward guard is lifted.
4. **A marker is not a gesture:** `undoOp`, `redoOp`, `foldBackGroup`, `foldForwardGroup` skip `op_type IN ('UNDO','REDO')`, so a second undo goes to the gesture before, not to the last marker.
5. **Stated limits:** the door does not judge signatures yet (item 3, door-side roster), so the door applies every marker in the file; the other §55 guarded paths (Team rebuild, relay sync, restore, legacy migration) stay guarded.

## 59. Enforce the pin in the fold: rows without a trusted signature stop affecting the page (2026-11-18, owner "proceed as u deem fit"; spec before the code)

**Rule (file mode only; nothing changes with no folder attached):**
1. **Admission is per row, not per chain.** After the sidecar is built from the file, every row's SIGNATURE is checked against {this device's key, the pinned keys}: v2 rows over the content hash (`KernelOps._contentHash`), v1 rows over `op_hash`; a row with no signature is not admitted. ## 52. §48 step 2: the door signs its ops (2026-11-18, owner: "the ledger"; spec before the code)
**Issue (measured in §48, re-read today on bim-ootb main `700fbdcb`):** the page's ops carry `op_uuid`, a ms timestamp, `prev_hash`, `op_hash`, `sig`; the door's lines carry none, so a door op cannot join the page's chain. A shared ledger needs the door to be one more signing device.

**Measured while writing this spec:**
- The page's chain is `erp/kernel_ops.js` over a `kernel_ops` row: `op_hash = sha256(prev + '|' + id|timestamp|op_type|parameters|input_guids|output_guid)` (`_canonical`, `:349`), sealed by `sealFrom` (`:408`) and checked by `verifyChain` (`:707`). The page turns on content signing (`idempiere.html:1169` `setContentSigning(true)`): each new op's `parameters` gets `_sigv:2` and `signed_by` (the device's public key, hex) inside it, and the sig attests `sha256('cs2|' + _canonicalV2(op))`, which holds no `id` and no `prev_hash`. So a v2 sig survives a renumbering (a merge); the chain hash does not.
- The signer is `erp/erp_signer.js` `makeSigner(keyPair)`: ECDSA P-256, SHA-256, over the hex string's bytes. It needs WebCrypto only; Node 18 has `globalThis.crypto` here. `kernel_ops.js` already runs in Node under `global.window = {}` (precedent: `erp/tests/witness_cross_tab_persist.js`).
- The door has THREE writers of the op-log: `object_cli.js:244` `persist`, `erp_cli.js:427` (an engine group), `erp_cli.js:938` (the held Ninja CSV batch). Readers: `object_cli.js` `readOps`, `sideDbOf` (already a `kernel_ops` table, without chain columns), and the op-image cache keyed on the log's bytes (`erp_cli.js:87-100`).
- No lock exists today: two door processes appending at once is harmless to a bare op list, but a chain forks if both take the same `prev_hash`.

**Rule (one implementation per responsibility, AD-LAYER LAW 5):**
1. **The door's chain IS the page's chain, by the same formulas.** The door's writers are SYNCHRONOUS (`persist`, `persistGroup` are called from dozens of sync paths; making them async would ripple through all of them), while `KernelOps.sealFrom` and `makeSigner` are async (WebCrypto). So a new `common/door/ledger_sign.js` takes the FORMULAS from `erp/kernel_ops.js` itself (loaded in an isolated `vm` context, so no `window` global leaks into the door: `_canonical`, `_canonicalV2`, `stableStringify`) and only the two PRIMITIVES from Node's sync `crypto` (sha256; ECDSA P-256 with `dsaEncoding: 'ieee-p1363'`, the WebCrypto signature format). It writes no canonical form of its own; G2 and G3 prove the bytes are the page's by running the page's own async verifier over the door's log.
2. **One line = one `kernel_ops` row, verbatim** (`id` = the 1-based line number, `op_uuid`, `timestamp` ms, `op_type`, `parameters` as the STORED string, `prev_hash`, `op_hash`, `sig`, `user_tag`). The door's op (`{op_type, table, fields, ...}` plus `t`) is the `parameters`. A reader accepts both shapes: a bare legacy op, or a row (its op = `JSON.parse(parameters)` minus `_sigv`/`signed_by`). Step 3 then copies rows; nothing is converted.
3. **All three writers go through one `ledger_sign.append(opfile, ops)`.** It takes `<opfile>.lock` (`wx`, stale after 10 s), re-reads the last line's `op_hash` under the lock, seals, appends, releases. A boot or a read verb never writes.
4. **Key custody:** a P-256 key in `~/.config/red1/door_key.json` (JWK, dir 0700, file 0600), minted once and reused; `RED1_DOOR_KEY` names another file (witnesses). `signed_by` = the SPKI hex, the same identity string the page stamps. Not non-extractable (a file on disk cannot be); that is the cost of a CLI and is stated, not hidden.
5. **A log that already exists** (bare lines): the first append, under the lock, seals the whole file in place: copy to `<opfile>.pre-seal`, write the rows to a temp file, rename. Each bare line becomes a row (`timestamp` = `Date.parse(t)`, a fresh `op_uuid`). Replay is unchanged because the op comes back out of `parameters`. The op-image cache sees changed bytes and rebuilds (its own rule).
6. **No new verb** (a verb costs about 13 places, §36). The check is a script: `node common/door/ledger_sign.js verify <opfile>` prints `§LEDGER verify OK len=N tip=...` or `brokeAt=<id> why=<...>`.

**Witness W-DOOR-SIGN** (`common/door/tests/witness_door_sign.js`; op-log, journal and key in a temp folder; the door makes an order with two lines, completes it, attaches a note, as W-ONE-FOLD does):
- G1 every line is a row with a uuid, a ms `timestamp`, `prev_hash`, `op_hash`, `sig`; ids run 1..N with no gap.
- G2 `KernelOps.verifyChain` over the log (loaded into a `kernel_ops` table, the page's own verifier, with the door's public key as the verifier) is `ok`, `len` = N.
- G3 the page's own `erp_signer.makeSigner`, handed the door's PUBLIC key, accepts every `sig` (the page can check the door).
- G4 the fold is unchanged: the door's database after replay equals the one from the unsigned log (the W-ONE-FOLD K4 comparison; same keys, same cells).
- G5 tamper: change one cell inside line k's `parameters`: verify FAILS at k; flip one hex digit of line j's `sig`: FAILS at j with `signature`.

## 49. §48 step 1: the page keeps the key a door record carries (2026-11-18, owner: "1"; spec before the code)
**Issue (measured in §48):** the page's fold (`crud_core.listTip`) gives every new record the key `-opId`, overwriting the key the op carries. A door order read by the page loses its lines: `c_project 990001 -> -1`, while `c_projectphase.c_project_id` stays 990001.

**Measured while writing this spec (bim-ootb main `2a6371e2`):**
- The page's `-opId` is deliberate, not an accident. Its model layer strips a new row's own key from the op (`model_layer.js:230`, "the host assigns it (listTip -opId)"), and `_resolveOpRefs` (`crud_overlay.js:3042-3060`) writes `-(nextId+i)` into the FKs of rows made in the same group. About 20 page modules write `CRUD_CREATE` ops. Changing the rule for EVERY op would re-key rows already saved in users' browsers (a later update that names `-opId` would miss its row).
- The door writes a self-contained op: `erp_cli.js:403` `resolveOne` puts the key (max+1) and `idCol` into the op before it is logged. The door's other write path, `object_cli.js:233` `persist` (used by `object.attach`), logs a create WITHOUT its key; `applyOp` picks max+1 at every replay.
- Legacy keeps a received key only for a replica (`PO.java:3530-3535`, `isReplication() && get_ID() > 0`); the model layer already has that rule as `keepKey` (`model_layer.js:163-164`).

**Rule:** a `CRUD_CREATE` op that carries `keyKept: true` and a positive integer key in `fields[<key column>]` keeps that key in the page's fold (`listTip`) and in its change log (`changeLog` / `_clFold`). Every other op folds as today (`-opId`). The door stamps `keyKept: true` on every create it logs on a table with a physical key column, in both write paths; `persist` now writes the key into the op (max+1, as `applyOp` would), so a replay never picks a new one.

**Changed from the first spec line (§48 step 1, "the door's applyOp is retired for listTip"):** refused on measurement. `applyOp` runs INSIDE the door's open transaction, one op at a time, on the in-memory database (`erp_cli.js:424`, under `SAVEPOINT erp_group`), so the next model read sees the row. `listTip` rebuilds a whole table's rows from the full op list on every read. Swapping them would turn each op of a group into a table rebuild. Instead, the witness proves the two folds give the SAME rows for a door log (the one-rule half of AD-LAYER LAW 5); the page keeps its shadow, the door keeps its live table.

**Witness W-ONE-FOLD** (bim-ootb `common/door/tests/witness_one_fold.js`; op-log + journal in a temp folder; the door makes an order with two lines, completes it, attaches a note):
