## 4. MEMORY

**VERDICT: The JS heap during the bake is moderate (Hospital 296-657 MB, LTU 407-1,426 MB by the CLI's CDP probe), and the single largest JS event is LTU's bounce-engine build (+~900 MB transient). The two heap instruments disagree 4-5× (CDP `JSHeapUsedSize` vs `performance.memory.usedJSHeapSize` 2.0-2.6 GB), neither counts typed-array backing stores or GPU memory, and no log line measures VRAM — so the biggest consumers named below are GPU-side and only partly measured. The §LOADPATH unbatch (4,983→73,797 objects) no longer happens in this film.**

### Ranked by evidence (MB where the log gives one)
1. **Light field, resident by design: 113.8 MB (Hospital) / 98.7 MB (LTU) unpacked in JS.** `§LIGHT_FIELD_DB restore … bytes=6940807 raw=125401424 … MB=113.8 heapMB=1100` (Hospital +7.3 s); LTU `raw=105549896 MB=98.7 heapMB=1416`. ## 5. SPEED

**VERDICT: Both bakes are CPU draw-call bound, as the foundation's "NEXT speed lever" said. LTU is 2× Hospital per frame because it submits 2.1× the draw calls for the SAME triangle count (LTU renderInfo mean 6,349 calls / 7.35 M tris vs Hospital 3,019 / 7.18 M); LTU's model streams into ~6,000 BatchedMesh + 1,896 InstancedMesh objects because the consolidation that exists for exactly this (`A._consolidateBatched`, streaming.js:3404) has no caller. A film frame runs 15 WebGL scene renders (hold 1 + TAA 6 + AO 6 + capture 1 + meter 1) plus the WebGPU bounce pass; every one of them pays the call count. Top lever: draw-call consolidation, look-neutral, worth roughly half of LTU's frame time.**

Why LTU draws 2.1× the calls: `§INST_RGBA_SPLIT building total hashes=3078 extraGroups=3106 elements=8015` (LTU) vs `hashes=27 extraGroups=27 elements=244` (Hospital) — LTU has per-element colours, so every (geometry hash, rgba) pair becomes its own InstancedMesh (`§FRAME_COST instancedMeshes=1896 instances=9746` = 5 instances per mesh; Hospital `instancedMeshes=2897 instances=90098` = 31). Result: `§GI_FILM_CENSUS visible … inst=1896 batched=5999` and `§RENDER_INFO capture=1 sceneCalls=9769 sceneTris=13965010`, `§FRAME_COST frustumPct=99.8%` (the whole house is in frame on the exterior shots). Hospital's last flush already merges well: `§BATCHED_FLUSH instanced=1223 batched=1459 drawCalls=238 (was 2682)`; LTU's: `instanced=40 batched=1790 drawCalls=140 (was 1830)` for one flush of 22.

### Top 3 algorithmic speedups (per frame, arithmetic from the logs)
1. **Consolidate draw calls (LTU-class models). Look-neutral.** Wire `A._consolidateBatched()` after streaming ends (one BatchedMesh per bucket across flushes) and carry rgba as `instanceColor` instead of splitting InstancedMesh groups (both three features are already used: setColorAt in cpe_storey_reveal.js). Expected: LTU mean 6,349 → ~3,000 calls (Hospital's density on the same triangle count) × 0.69 ms = **≈ −2.3 s/frame of 3.83** (first-order; the fit's intercept is ~0 so this is an upper bound) — floor estimate from the buckets alone: the 368 slow frames (6.17 s, 9,245 calls) brought to the fast bucket's 2.07 s = 368 × 4.1 s = 25 min of the 106-min bake. Hospital gains less (already ~3k calls; the lever there is its 2,897 InstancedMesh with RGBA splits = 27 only). Witness: `§BATCH_CENSUS batched= instanced= mesh= calls= tris=` at frame 0, `§FRAME_QA` luma vs control ≤ the ctrl/ctrl2 floor (0.12), `§GI_FILM errFrames=0`. Effort: 1-2 days (the function exists; wiring + witness + an LTU slice run).
2. **The meter's own scene render: LTU 488 ms (12.8%), Hospital 164 ms (8.0%) per frame.** `SourcedLight.meterRead` renders the scene at 160×90 every frame (`§FILM_EXPOSURE … ms=`); it is submission-bound, so it shrinks with item 1 (at ~3k calls LTU would pay about Hospital's 164 ms: −324 ms). Beyond that: meter from the previous frame's finished 64×36 (`§FRAME_QA` already computes it) — one-frame lag, **look-affecting (exposure)**, red1 decides; §SPEED_AB arm B showed a 4-frame skip costs 0.71 EV, a 1-frame lag is bounded by LightLaw.ADAPT × 1/24 s and must be measured (`§FILM_EXPOSURE` EV delta vs control).
3. **The hidden 13th TAA sample at capture (budget 6/6): LTU 179 ms (4.7%), Hospital 51 ms (2.5%).** `_captureFrame` :1683 `A._composer.render()` runs TAARenderPass.render (lib/TAARenderPass.js:73-111): `accumulate` is still true (reset only in `_teardownStillRefine`, effects.js:5750) and `accumulateIndex` = 12 < 16 after 6 TAA + 6 AO samples, so the pass renders one more jittered scene sample. At the default 8/8 the index is 16 and no render happens — the 6/6 recipe added this render silently; §SPEED_AB's own table shows it (arm C capture 824 ms vs arm A 433 ms, +391 ms on heavy frames). Two facts for red1: (a) skipping it (set `accumulateIndex=16` before the capture render, or count it in the budget as 5/6) saves the composer part but changes 13→12 of 16 samples; (b) at 6/6 the shipped picture already blends 3/16 of the unjittered hold frame (TAARenderPass.js:118-137 `accumulationWeight < 1.0` branch) — **look-changing either way, red1's call**; the §SPEED_AB C arm (PSNR 44.1 ≈ floor) covered 12+1 samples, not 12.
Also (smaller, look-neutral): 4. defect 1C (stable data lamp set): rebuild frames' light phase +86 ms (LTU, 40% of frames → ~34 ms/frame) / +388 ms (Hospital, 10.3% → ~40 ms/frame), and it removes lamp popping — but feeding all 1,503 fixtures is look-changing toward Alt+S parity (more lamps lit): red1. 5. Per-frame still teardown/restart (§2 item 2) and the two `_raf2` ticks (cinema_maxq.js:3602, 4136): the setup phase is 299-440 ms/frame but the log cannot split it (no `renders=` counter; the foundation's §BAKE_LEAN L1+L2 measured no gain on HHS) — INCONCLUSIVE until the §F record's `renders=` lands. 6. SHA-256 of the JPEG blob is awaited inline (`§CAPTURE_TAIL hashMs=23-45`): move to a worker or hash in the IDB write path, −23..45 ms (≈1%), trivial.
