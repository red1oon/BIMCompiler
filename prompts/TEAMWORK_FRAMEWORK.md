## ⚖ IMMUTABLE TWIN PRINCIPLE — LOCAL FIRST + MINIMAL DATA RELAY (owner, 2026-10-26: *"Ensure the twin principle of local first, network data relay relay is immutable."* … *"Minimal relay that is"*)
**(1) Local first:** every device works on its own full copy (the BASE + its own log); nothing in the sale path, the edit path or a document's life waits on the network. **(2) Minimal data relay:** the network is a dumb post office that only carries the minimum that identifies (ids, references, measures, codes — FL-1); it runs no business logic, holds no truth, and is never asked a question in real time. **Immutable = no design, treatment, flow row, host change or film may add a server in the path, a realtime check, or a fat payload** — the community-fork habit of making returns and loyalty realtime (a server validates the return, a server holds the points) is exactly what this forbids; the documented workarounds (§16.17 rows 2/3/10, the INSTRUMENT treatment, FL-7 deterrence, DistributedERP §5) are the only accepted forms. Corollaries already in force: one DocAction executor per document, results never broadcast beyond the declared flows (FL-8); derived values recomputed, never copied (FL-2). **Planned enforcement (spec, §39):** the compiler refuses a row that needs an online round-trip (`realtime-in-path`), and refuses a row with no `carries` on a declaration (`fat-declaration`). The one named exception that DistributedERP §5 still keeps — an online compare-and-set for a high-value, anonymous, divisible balance — is ⛔ an owner decision under this principle (§39 R9).
**(3) Abstraction over custom code — ALREADY recorded, not restated here:** §16.16 (owner 2026-10-25: *"Replication table can come in handy to abstract such rather than custom make each"*), §19 design intent (*"remove custom code and have abstract implementation that can scale"*), tests `W-FLOW-ZERO-CODE` (§16.16) and `W-TREAT-ZEROCODE` (§16.18). ### §16.0a Doctrine from the Unicenta POS integration (user, 2026-10-25: *"I am a guru on this Unicenta POS story as I built the integration"*)
> *"…with a full seed local, you only need to send a minimal payload across. Even stock checking is not needed on POS side, because admin side has the full picture when an orderline with product and qty sold. Yes POS side has deducted its stocks from each sale, that is for its own info but maybe 2 sources of truth and thus redundant. POS just goes on selling. If it cheats ie under declare, it ends up in trouble as less stocks replenish. This is something i grasp as quantitative methods of Edward Deming… The AD design of having a lookup ID in PK form is a big hint how we need not store core tables. And passing PK/FK is encrypted enough… that is the truth and integrity in minimal form."*
The shape of the Unicenta integration: **up** = order lines (product, qty) from each POS to HQ; **down** = replenishment (product_id, qty) from HQ to the one station that needs it; nothing else crosses. The scriptor's unit is therefore a **flow**, not a table set.
- **FL-1 Seed once, send minimal.** Every device holds the master data (the BASE: dictionary + master tables, hash-pinned, §13.12.I). A flow carries only record identity, references (ids resolved in the receiver's base), measures (qty, amount, date) and codes. Descriptive text is not carried; its meaning lives in the base.
- **FL-2 One place holds the truth per fact class; the point of action declares, the centre derives.** The POS declares sales; HQ derives stock (a sum over declared movements — the thesis sentence in `docs/DistributedERP.md`) and answers with replenishment. A POS-local deduction is an advisory copy. Each fact has one author, so §11.2 "one writer per name" already prevents the conflict. **Reworded 2026-10-25 (§16.18b): the invariant is *one derivation function*, not one place — in a star one device (the hub) runs it; in a mesh every member runs the same deterministic fold and reaches the same result; either way a derived value is never copied from one device to another.**
- **FL-3 Feedback instead of inspection (Deming).** No synchronous stock check and no arbiter for stock: under-declaring starves the declarer of replenishment. *(inference from the user's account)* the "last unit of stock" row of §13.11 then needs no arbiter in this pattern — a stock-out is a business consequence, not an integrity failure. Remaining arbiter cases are listed in the §16.14 amendment.
- **FL-4 Limits to test, not assume.** *(inference)* The incentive holds where the declarer bears the consequence (stock). It does not police cash or value taken outside the system, and it does not detect *over*-declaration; those need an independent flow (payments, a periodic count — the pawn day-end count, `PAWN_FINTECH_SPEC.md` §20.5).
- **FL-5 Ids are pseudonymous, not confidential.** Without the seed an id means nothing — real data minimisation. But ids are small sequential integers, a seed can be public (GardenWorld), and volume and timing stay visible, so flows are still sealed (CL8, §13.4). References to seed rows use the seed key (identical on every device because the base is hash-pinned); references to records created on a device use `<table>_uu` (§11.1).
- **FL-8 UPS — the Unicenta POS Strategy: ONE DocAction, at the processor (owner, 2026-10-26: *"UPS is Unicenta POS Strategy. Which we already noted prior that it does not need to handle Docaction locally as there's no need to do any posting. At server those are done to return just replenish movement. Harden the specs to grasp this UPS well as dual Docaction may results on ghost and loss of single source of truth."*).** (a) The point of action (the POS station) only DECLARES: the lines (product, qty, uom) under its ticket key POSStation/Date/Order# (§16.16a). It does NOT complete, post, reserve, or create shipments or invoices — **no DocAction on the station**; its own stock deduction is an advisory copy (FL-2). (b) The PROCESSOR (the HQ/server role) receives the declaration, authors the document, runs the DocAction **once** (Complete + posting), and returns only what the station needs: the **replenishment movement** (product, qty). (c) **Every document has exactly ONE DocAction executor, named by the plan.** No other device runs completeIt / posting for it — not even "deterministically". Reason, measured: a second run mints its own ids (1–3 generated uu per Complete, §36.1 T3(e)), its own document numbers (§36.1 T3(b)) and its own Fact_Acct lines → **GHOST records** (two shipments, two postings for one sale) and **a second source of truth** that can drift. (d) FL-2's 2026-10-25 reword ("in a mesh every member runs the same fold") covers derived VALUES that are recomputed and never stored as records of their own (a stock sum, a balance, a rank). **It never licenses running a DocAction or a posting on more than one device.** (e) The single run's consequences are not broadcast either: each other role receives only the flows the plan declares for it (the station: replenishment). In a peer team (mesh) the executor of a document is its author's device (or the role the plan names); the others receive its declared outputs — they never re-run it. **Planned witness `W-UPS-ONE-DOCACTION` (spec only, not built):** COMPILE — a plan in which two roles could run a DocAction on the same document flow, or a station role is given one, is REFUSED (`dual-docaction` / `station-docaction`); SIMULATOR — a station that completes a declared ticket is caught (its derived rows have no counterpart at the processor = ghost count > 0) and the processor's single run is the only source of M_InOut / Fact_Acct for that ticket; MUTANT — allow a second executor → the ghost arm turns red. **ENFORCED, not just described (owner, 2026-10-26: *"So the Replication Engine enforces that well besides dictating such data flow."*) — today NOTHING enforces FL-8 (the plan is `tables-only`; any device can Complete and its whole consequence group is broadcast); the engine must enforce it in three layers, each witnessed:** **E1 COMPILE** — a document flow row names its ONE executor role (`docaction: {role, actions}`); the compiler refuses a plan with two executor roles for the same document type (`dual-docaction`) or a station/declaring role as executor (`station-docaction`). **E2 LEGACY ACCESS (twin, same L&F)** — the compiled plan is projected onto iDempiere's OWN mechanism, `AD_Document_Action_Access` (per role × document type × action; legacy check `MRole.checkActionAccess`, `MRole.java:2685`; already read by our model layer, `erp/model_master.js:335`): a station role simply has no Complete in its DocAction list, exactly as a legacy role without that access would see it — no new UI rule. **E3 ADMISSION (every device, same verdict)** — the comm fold refuses a DocAction op group whose author's role is not the plan's executor for that document type: `REFUSED not-executor` (same pattern as `not-admin`), so a modified or rogue device cannot introduce a second source of truth — its ghost rows never reach anyone's books, and the refusal is visible. `W-UPS-ONE-DOCACTION` judges E1 (compile refusals), E2 (the projected access rows = the plan, X of N document types) and E3 (a station-authored Complete REFUSED `not-executor` on every device; the processor's Complete MERGED; mutants: E3 check off → the ghost arm red; E1 check off → the dual plan compiles). *(Numbered FL-8 on 2026-10-26: it was first written as "FL-7", which already names deterrence over prevention, §16.17 — the commit messages 043597bea…38f359444 say "FL-7 UPS"; ### §45.12 UNWRAP MEMO — the sealing-era slowdown (lead, 2026-11-01; SPEC BEFORE CODE, witness RED first; NEXT #1 of the 2026-11-01 STATE)
**Issue it proves/disproves.** After §45.11, W-SCALE-STAR engine at N=100 takes 118 s against 44 s for the F1 engine, peak RSS 337 vs 270 MB (`build/scriptor/perf_review_20261101/scale_summary.log`). Counting WebCrypto calls from outside the product (`count_unwrap.js`, `count_distinct.js`): the founder/hub process makes **62,168 `unwrapKey` calls for 210 distinct wrapped grants** (`scale_new_100_distinct.log`, `§UNWRAP_DISTINCT … total=62168 distinct_wrapped=210`), 1,006 at N=10: roughly quadratic. Each call also costs a `deriveBits` (ECDH) + `deriveKey` (HKDF), so 62,770 of each. Cause, read in the code: `keyring()` (`common/comm/comm_store.js:415-426`) is memoised on the fold result (`ringFor === L`); every new op makes a new fold result, so it re-unwraps EVERY grant addressed to me. A hub receives a new pair-key grant per bound device (§45.11), so grants × folds grows like N².
**Fix.** A per-store cache of opened grants, keyed on everything the unwrap depends on: `wrapped | from_kid | epoch | aud | from.dh (x,y)` (self kid and private key are fixed for the store). The value is the CryptoKey, or a "does not open" marker (so a bad grant is not retried every fold; a new `from.dh` gives a new key and is tried again). The **ring is still rebuilt from the CURRENT fold's `R.grants` every time** (cheap: map lookups), so a grant the roster no longer accepts drops out exactly as today; only the crypto is memoised. ## §52 TRIPLE REDUNDANCY — durability ladder + restore drill (name: owner, 2026-11-01: *"we can call this 'Triple Redundancy', something that even serverful systems need but ours is better and low cost and risk"*.
