## ⚖ IMMUTABLE TWIN PRINCIPLE — LOCAL FIRST + MINIMAL DATA RELAY (owner, 2026-10-26: *"Ensure the twin principle of local first, network data relay relay is immutable."* … *"Minimal relay that is"*)
**(1) Local first:** every device works on its own full copy (the BASE + its own log); nothing in the sale path, the edit path or a document's life waits on the network. **(2) Minimal data relay:** the network is a dumb post office that only carries the minimum that identifies (ids, references, measures, codes — FL-1); it runs no business logic, holds no truth, and is never asked a question in real time. **Immutable = no design, treatment, flow row, host change or film may add a server in the path, a realtime check, or a fat payload** — the community-fork habit of making returns and loyalty realtime (a server validates the return, a server holds the points) is exactly what this forbids; the documented workarounds (§16.17 rows 2/3/10, the INSTRUMENT treatment, FL-7 deterrence, DistributedERP §5) are the only accepted forms. Corollaries already in force: one DocAction executor per document, results never broadcast beyond the declared flows (FL-8); derived values recomputed, never copied (FL-2). **Planned enforcement (spec, §39):** the compiler refuses a row that needs an online round-trip (`realtime-in-path`), and refuses a row with no `carries` on a declaration (`fat-declaration`). The one named exception that DistributedERP §5 still keeps — an online compare-and-set for a high-value, anonymous, divisible balance — is ⛔ an owner decision under this principle (§39 R9).
**(3) Abstraction over custom code — ALREADY recorded, not restated here:** §16.16 (owner 2026-10-25: *"Replication table can come in handy to abstract such rather than custom make each"*), §19 design intent (*"remove custom code and have abstract implementation that can scale"*), tests `W-FLOW-ZERO-CODE` (§16.16) and `W-TREAT-ZEROCODE` (§16.18). ### §16.0a Doctrine from the Unicenta POS integration (user, 2026-10-25: *"I am a guru on this Unicenta POS story as I built the integration"*)
> *"…with a full seed local, you only need to send a minimal payload across. Even stock checking is not needed on POS side, because admin side has the full picture when an orderline with product and qty sold. Yes POS side has deducted its stocks from each sale, that is for its own info but maybe 2 sources of truth and thus redundant. POS just goes on selling. If it cheats ie under declare, it ends up in trouble as less stocks replenish. This is something i grasp as quantitative methods of Edward Deming… The AD design of having a lookup ID in PK form is a big hint how we need not store core tables. And passing PK/FK is encrypted enough… that is the truth and integrity in minimal form."*
The shape of the Unicenta integration: **up** = order lines (product, qty) from each POS to HQ; **down** = replenishment (product_id, qty) from HQ to the one station that needs it; nothing else crosses. The scriptor's unit is therefore a **flow**, not a table set.
- **FL-1 Seed once, send minimal.** Every device holds the master data (the BASE: dictionary + master tables, hash-pinned, §13.12.I). A flow carries only record identity, references (ids resolved in the receiver's base), measures (qty, amount, date) and codes. Descriptive text is not carried; its meaning lives in the base.
- **FL-2 One place holds the truth per fact class; the point of action declares, the centre derives.** The POS declares sales; HQ derives stock (a sum over declared movements — the thesis sentence in `docs/DistributedERP.md`) and answers with replenishment. A POS-local deduction is an advisory copy. Each fact has one author, so §11.2 "one writer per name" already prevents the conflict. **Reworded 2026-10-25 (§16.18b): the invariant is *one derivation function*, not one place — in a star one device (the hub) runs it; in a mesh every member runs the same deterministic fold and reaches the same result; either way a derived value is never copied from one device to another.**
- **FL-3 Feedback instead of inspection (Deming).** No synchronous stock check and no arbiter for stock: under-declaring starves the declarer of replenishment. *(inference from the user's account)* the "last unit of stock" row of §13.11 then needs no arbiter in this pattern — a stock-out is a business consequence, not an integrity failure. Remaining arbiter cases are listed in the §16.14 amendment.
- **FL-4 Limits to test, not assume.** *(inference)* The incentive holds where the declarer bears the consequence (stock). It does not police cash or value taken outside the system, and it does not detect *over*-declaration; those need an independent flow (payments, a periodic count — the pawn day-end count, `PAWN_FINTECH_SPEC.md` §20.5).
- **FL-5 Ids are pseudonymous, not confidential.** Without the seed an id means nothing — real data minimisation. But ids are small sequential integers, a seed can be public (GardenWorld), and volume and timing stay visible, so flows are still sealed (CL8, §13.4). References to seed rows use the seed key (identical on every device because the base is hash-pinned); references to records created on a device use `<table>_uu` (§11.1).
- **FL-8 UPS — the Unicenta POS Strategy: ONE DocAction, at the processor (owner, 2026-10-26: *"UPS is Unicenta POS Strategy. Which we already noted prior that it does not need to handle Docaction locally as there's no need to do any posting. At server those are done to return just replenish movement. Harden the specs to grasp this UPS well as dual Docaction may results on ghost and loss of single source of truth."*).** (a) The point of action (the POS station) only DECLARES: the lines (product, qty, uom) under its ticket key POSStation/Date/Order# (§16.16a). It does NOT complete, post, reserve, or create shipments or invoices — **no DocAction on the station**; its own stock deduction is an advisory copy (FL-2). (b) The PROCESSOR (the HQ/server role) receives the declaration, authors the document, runs the DocAction **once** (Complete + posting), and returns only what the station needs: the **replenishment movement** (product, qty). (c) **Every document has exactly ONE DocAction executor, named by the plan.** No other device runs completeIt / posting for it — not even "deterministically". Reason, measured: a second run mints its own ids (1–3 generated uu per Complete, §36.1 T3(e)), its own document numbers (§36.1 T3(b)) and its own Fact_Acct lines → **GHOST records** (two shipments, two postings for one sale) and **a second source of truth** that can drift. (d) FL-2's 2026-10-25 reword ("in a mesh every member runs the same fold") covers derived VALUES that are recomputed and never stored as records of their own (a stock sum, a balance, a rank). **It never licenses running a DocAction or a posting on more than one device.** (e) The single run's consequences are not broadcast either: each other role receives only the flows the plan declares for it (the station: replenishment). In a peer team (mesh) the executor of a document is its author's device (or the role the plan names); the others receive its declared outputs — they never re-run it. **Planned witness `W-UPS-ONE-DOCACTION` (spec only, not built):** COMPILE — a plan in which two roles could run a DocAction on the same document flow, or a station role is given one, is REFUSED (`dual-docaction` / `station-docaction`); SIMULATOR — a station that completes a declared ticket is caught (its derived rows have no counterpart at the processor = ghost count > 0) and the processor's single run is the only source of M_InOut / Fact_Acct for that ticket; MUTANT — allow a second executor → the ghost arm turns red. **ENFORCED, not just described (owner, 2026-10-26: *"So the Replication Engine enforces that well besides dictating such data flow."*) — today NOTHING enforces FL-8 (the plan is `tables-only`; any device can Complete and its whole consequence group is broadcast); the engine must enforce it in three layers, each witnessed:** **E1 COMPILE** — a document flow row names its ONE executor role (`docaction: {role, actions}`); the compiler refuses a plan with two executor roles for the same document type (`dual-docaction`) or a station/declaring role as executor (`station-docaction`). **E2 LEGACY ACCESS (twin, same L&F)** — the compiled plan is projected onto iDempiere's OWN mechanism, `AD_Document_Action_Access` (per role × document type × action; legacy check `MRole.checkActionAccess`, `MRole.java:2685`; already read by our model layer, `erp/model_master.js:335`): a station role simply has no Complete in its DocAction list, exactly as a legacy role without that access would see it — no new UI rule. **E3 ADMISSION (every device, same verdict)** — the comm fold refuses a DocAction op group whose author's role is not the plan's executor for that document type: `REFUSED not-executor` (same pattern as `not-admin`), so a modified or rogue device cannot introduce a second source of truth — its ghost rows never reach anyone's books, and the refusal is visible. `W-UPS-ONE-DOCACTION` judges E1 (compile refusals), E2 (the projected access rows = the plan, X of N document types) and E3 (a station-authored Complete REFUSED `not-executor` on every device; the processor's Complete MERGED; mutants: E3 check off → the ghost arm red; E1 check off → the dual plan compiles). *(Numbered FL-8 on 2026-10-26: it was first written as "FL-7", which already names deterrence over prevention, §16.17 — the commit messages 043597bea…38f359444 say "FL-7 UPS"; ## §46 G-10 as an OSGi-style release — spec, and the dangers of the new shape (owner, 2026-10-29: *"Actually OSGi has a standard too, plugin versioning, to solve such hell that cuts across everyone. … Yes. Do you foresee any dangers? I am thinking of what scenario in this new shape can break it."*)
**Today (measured 2026-10-29):** two versioning schemes. (a) Plugins, in `erp/plugin_registry.js`: semver, mandatory `version`, an `engineVersion` gate, `requires` checked with SINGLE-comparator ranges (`*`, `=`, `>=`, `>`, `<=`, `<`), and `resolveDeps` refusing a missing dependency, a conflict or a cycle. (b) Team op shapes, in `common/comm/op_versions.js`: a per-op-type version; upcasters as SIGNED DATA; `v > appV` → PARKED `needs-upgrade`; a missing step → PARKED `needs-mapping`; **`v < min_v` → REFUSED `retired-version` (`:101`)**. And **no base-upgrade path**: changing a hashed base file forces re-founding (`W-BASE-RELEASE` out of scope, :2293).
**Spec:**
- **ONE versioning scheme** for plugins and op shapes, OSGi semantic versioning: `major.minor.micro`; a minor or micro change is backward compatible and a major is breaking; dependencies and compatibility as two-sided OSGi ranges (`[1.2,2)`). The plugin registry gains two-sided ranges, the op shapes adopt the same numbers, and one parser serves both (deletion budget: the two separate version parsers go).
- **A release** = a signed package: the Pack Out contents (dictionary / plan / translation rows), its version, its compatibility range, and `prev`, the hash of the release it follows (chained, as trusted keys and executor maps are).
- **Screens, inside Plugins & Releases**, industry words with the legacy name in brackets: **Publish schema update** (Pack Out), **Rollout** (Packages Installed: adopted by N of M devices, who is behind, why), **Trusted keys** (a chained history), **Sync rules** (Replication Strategy, read-only).

### §46.2 Module TTL: "this code has expired, check for updates" (owner, 2026-10-29: *"Thinking also the version control can set each module a TTL so it can warn user code has expired and need to check back for updates."*)
**Industry name:** an **expiry on signed metadata**: TUF puts an `expires` date on every signed role file, so that a device cut off from updates (by accident, or by someone blocking them: TUF calls it a *freeze attack*) does not keep believing it is current. **Spec:** every release and every plugin bundle carries `expires` in its signed manifest (set by the publisher, e.g. 90 days). When it passes, the device shows *"<module> <version> expired on <date>. Connect to check for updates."*: in the Team chip, in Plugins & Releases, and on the module's own screen. **The rules that keep it safe in local first:**
- **It warns; it never stops business.** A till keeps selling, and a phone keeps declaring slips, on an expired module: refusing work offline would break the immutable principle (no realtime dependency in the path). What expiry MAY hold back is publishing: an admin device on an expired release cannot publish a new one until it has synced, because it would otherwise publish on top of an out-of-date chain (D4).
- **Clock honesty (the D11 concern):** expiry is the one place a date is used, and it only raises a warning, so clock skew can only make the warning early or late, never change data. The device compares `expires` against the later of its own clock and the newest signed timestamp it has seen in the log, so winding the device clock back does not hide an expiry.
- **Renewal without a new build:** the publisher can extend `expires` with a signed renewal (the same chained statement, a new `expires`, the same contents). Devices adopt it at their next sync.
- **Witness arms:** expired → the warning text in all three places, and business still works (a till sale and a slip are accepted) · the clock set back below the newest signed timestamp → still expired · a signed renewal → the warning clears at the next sync · an admin on an expired release → publishing refused with the reason · mutant: expiry blocks a sale (must be caught).

##### U3 Binding and ordering (F8)
- Each entry binds `hash`+`size` of its release. On a device that holds the release bytes: recompute; mismatch (hash or size) = entry state `hash-mismatch` (never offered, `§UPD_ENTRY ... hash-mismatch`), the rest of the list still works.
- A list that arrives BEFORE its release: entry state `not-downloaded` ("update available, not yet downloaded"), never adopted; when the release arrives and matches: `update-available`.
- `withdrawn` (the `[YANKED]` tag) with a reason shows on every device, **never blocks business** and never refuses an already-folded op; a withdrawn entry that others `requires` marks each dependent `warn:depends-on-withdrawn`; a plugin's own `requires` stays a hard INSTALL refusal in the registry (the list can only warn).
- A receiver REFUSES a base-changing package: an entry with `base.sha256` different from the space's base (`ctx.base`) = state `refused-base-change` (re-founding is out of scope, `W-BASE-RELEASE`); the publish helper refuses to list it too (D7: enforced by receivers, not only at publish).
- `apply:'policy'` while the POLICY already carries `caps.policy_upcaster_sets` sets: state `apply-blocked-cap` with the reason "compact before applying" — shown, not hidden (release #17).

Expiry only WARNS ("Update list is out of date: connect to check"); TUF's "MUST NOT trust an expired file" is deliberately not followed (freeze protection is advisory) — stated in the Updates screen text and the log (`§UPD_EXPIRY_ADVISORY`).
Monotonic: the device remembers the highest accepted `{number, hash}`; a lower number = `list-replayed`; the same number with different content, or a `prev` that does not match the remembered previous list = `list-fork` (both shown to the admin, neither adopted).

##### U5 Changelog (§46.4 as corrected by F12)
Per entry `changelog = {Added, Changed, Deprecated, Removed, Fixed, Security}` (Keep a Changelog section names); each a list of `{what, why, action?, breaking?}`. ### §45.10 F1 PER-DEVICE MAILBOXES — owner GO 2026-10-31; background agent; spec written BEFORE the code (pasted verbatim), results lead-checked
###### §45.8 F1 BUILD SPEC - per-device mailboxes at the relay (agent F1, 2026-10-31; SPEC BEFORE CODE; witness RED first)

**Issue it proves/disproves:** §45.5 measured an edge's Visit #1 download growing linearly in N (367 KB / 4.5 MB / 45.8 MB at N=10/100/1000) because every device lists and downloads every other device's bundle and then refuses ~99% of it locally. F1 must make the edge's *business* download proportional to its OWN mail, flat in N.

**Measured facts the design rests on (read from code, file:line at origin/main c23e28cf):**
- The fold orders by `deps` ONLY: `comm_store.js:194` passes `prev: null` to `ORD.linearize`. The author chain `prev` is cosmetic for ordering, so an edge that does not hold every seq of HQ's chain parks nothing (no chain surgery needed). What a seq hole does touch: `gaps()` (`:499`), the `frontier()` receipt (`:491`), and the signed head's frontier (`:651`) which the SENDER reads as the ACK ("SEEN by").
- Admission by address is already done at the receiver (`team_sync.js:402-411`, `TeamScope.admits`): F1 changes only WHAT IS DOWNLOADED, never the verdict rule.
- The sender already computes the DOWN addressee (`team_sync.js:300-302`, `entityUu(by...)`, a `person_uu`); an UP flow's addressee is the plan's hub.

**Relay layout (the relay stays a dumb store of paths):**
- Shared stream, unchanged: `s/<space>/o/<kid>/<from>-<to>.<h12>.bimpack` - identity/roster/policy/key ops, office-team ops, and every op with no addressee. EVERY device lists/reads it, exactly as today.
- NEW mailbox: `s/<space>/m/<box>/o/<kid>/<from>-<to>.<h12>.bimpack`, `<box>` = `hub` (UP envelopes: head office's inbox) or `p_<person_uu>` (a DOWN envelope's addressee). `<kid>` = the AUTHOR (one-writer rule kept: `ghPipe._kidOfName` learns `m/<box>/o/<kid>` -> kid at index 5; the gate uses the same function; the `/o/<kid>/` inside the path is deliberate - the stock W-SCALE-STAR / W-HQ-HOTSPOTS load-generator filter admits a device's own `…/o/<kid>/…` names, so the unmodified harness keeps working). `from-to` = the first/last author seq inside that bundle.
- Heads `s/<space>/h/<kid>` unchanged (written by all).

**Who reads what (each device lists only its own mailbox):** a hub-role device reads `o/`, `m/hub/` and all heads. A non-hub device reads `o/`, `m/p_<its person>/` and only the heads of hub devices and of its own person's devices. The boxes are re-computed AFTER the shared stream was taken in the same Visit (the ENROLL that gives the device its role arrives in `o/`).

**Engine contract (comm_store.js, minimal):** `S.setMailbox({ laneOf(spec)->lane|null, read({roster,self})->[box], wantHead(kid,{roster,self})->bool })`. The host (the ERP adapter) supplies plan knowledge; the store knows no plan. - **Audience = the PAIR.** A laned op is sealed to one audience: lane `p_X` (DOWN to person X) → audience `p_X`; lane `hub` (UP) authored by a device of person X → audience `p_X`; lane `hub` authored by a hub device → audience `hub`. ### §51.1 C1 BUILD SPEC — the content-keyed witness cache (owner "Agree", 2026-10-31; SPEC BEFORE CODE; witness RED first)
**Issue it proves/disproves:** re-running a witness whose inputs did not change is pure waste (§51 measured ~40 min for 15 witnesses), BUT a cache that hits when an input DID change would print a stale PASS — worse than the waste. So the property judged is two-sided: **every input change misses; an unrelated change hits.** A miss is always safe; a wrong hit is the defect.
**Inputs are TRACED, not declared** (a hand-declared list under-declares silently). `scripts/witness_trace.js` is preloaded (`NODE_OPTIONS=--require`) into the witness AND every node child it spawns; it records, per process, every path the code reads (`readFileSync/readFile/promises.readFile/createReadStream/openSync/open/promises.open` with a read flag — so `require`, a page served by the witness's own HTTP server to headless Chromium, and a fixture read all count), every directory it lists (`readdir*`, hashed as the sorted name list), every existence probe (`existsSync/statSync/accessSync`, hashed as content-or-ABSENT), and every path it writes (excluded: a file the run itself wrote is output, not input). Kept: paths under the two trees (bim-compiler, bim-ootb); dropped: `node_modules/`, `.git/`, the cache dir, the run's own log dir.
**Key** = sha256(witness path relative to its tree · args · the env values the runner sets for it · node version). **Entry** (`~/.cache/bim-witness/<key>.json`) = the input list with each content hash + the log + exit. Stored ONLY for a passing run (exit 0) with ≥1 traced input (zero inputs = the tracer did not work → never cached, `§CACHE_SKIP reason=no-inputs`). **Hit** = every listed input re-hashes equal → the stored log is replayed with a line `§CACHED <witness> inputs=<n> key=<h12> from=<iso>`; nothing runs. **Uncachable (always runs, `§CACHE_SKIP reason=…`):** a node-executed file containing `import(` (Node's ESM loader reads files outside the patched `fs`, so those reads are invisible); `--fresh 1`.
