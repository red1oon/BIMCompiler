## ⚖ IMMUTABLE TWIN PRINCIPLE — LOCAL FIRST + MINIMAL DATA RELAY (owner, 2026-10-26: *"Ensure the twin principle of local first, network data relay relay is immutable."* … *"Minimal relay that is"*)
**(1) Local first:** every device works on its own full copy (the BASE + its own log); nothing in the sale path, the edit path or a document's life waits on the network. **(2) Minimal data relay:** the network is a dumb post office that only carries the minimum that identifies (ids, references, measures, codes — FL-1); it runs no business logic, holds no truth, and is never asked a question in real time. **Immutable = no design, treatment, flow row, host change or film may add a server in the path, a realtime check, or a fat payload** — the community-fork habit of making returns and loyalty realtime (a server validates the return, a server holds the points) is exactly what this forbids; the documented workarounds (§16.17 rows 2/3/10, the INSTRUMENT treatment, FL-7 deterrence, DistributedERP §5) are the only accepted forms. Corollaries already in force: one DocAction executor per document, results never broadcast beyond the declared flows (FL-8); derived values recomputed, never copied (FL-2). **Planned enforcement (spec, §39):** the compiler refuses a row that needs an online round-trip (`realtime-in-path`), and refuses a row with no `carries` on a declaration (`fat-declaration`). The one named exception that DistributedERP §5 still keeps — an online compare-and-set for a high-value, anonymous, divisible balance — is ⛔ an owner decision under this principle (§39 R9).
**(3) Abstraction over custom code — ALREADY recorded, not restated here:** §16.16 (owner 2026-10-25: *"Replication table can come in handy to abstract such rather than custom make each"*), §19 design intent (*"remove custom code and have abstract implementation that can scale"*), tests `W-FLOW-ZERO-CODE` (§16.16) and `W-TREAT-ZEROCODE` (§16.18). ### §16.0a Doctrine from the Unicenta POS integration (user, 2026-10-25: *"I am a guru on this Unicenta POS story as I built the integration"*)
> *"…with a full seed local, you only need to send a minimal payload across. Even stock checking is not needed on POS side, because admin side has the full picture when an orderline with product and qty sold. Yes POS side has deducted its stocks from each sale, that is for its own info but maybe 2 sources of truth and thus redundant. POS just goes on selling. If it cheats ie under declare, it ends up in trouble as less stocks replenish. This is something i grasp as quantitative methods of Edward Deming… The AD design of having a lookup ID in PK form is a big hint how we need not store core tables. And passing PK/FK is encrypted enough… that is the truth and integrity in minimal form."*
The shape of the Unicenta integration: **up** = order lines (product, qty) from each POS to HQ; **down** = replenishment (product_id, qty) from HQ to the one station that needs it; nothing else crosses. The scriptor's unit is therefore a **flow**, not a table set.
- **FL-1 Seed once, send minimal.** Every device holds the master data (the BASE: dictionary + master tables, hash-pinned, §13.12.I). A flow carries only record identity, references (ids resolved in the receiver's base), measures (qty, amount, date) and codes. Descriptive text is not carried; its meaning lives in the base.
- **FL-2 One place holds the truth per fact class; the point of action declares, the centre derives.** The POS declares sales; HQ derives stock (a sum over declared movements — the thesis sentence in `docs/DistributedERP.md`) and answers with replenishment. A POS-local deduction is an advisory copy. Each fact has one author, so §11.2 "one writer per name" already prevents the conflict. **Reworded 2026-10-25 (§16.18b): the invariant is *one derivation function*, not one place — in a star one device (the hub) runs it; in a mesh every member runs the same deterministic fold and reaches the same result; either way a derived value is never copied from one device to another.**
- **FL-3 Feedback instead of inspection (Deming).** No synchronous stock check and no arbiter for stock: under-declaring starves the declarer of replenishment. *(inference from the user's account)* the "last unit of stock" row of §13.11 then needs no arbiter in this pattern — a stock-out is a business consequence, not an integrity failure. Remaining arbiter cases are listed in the §16.14 amendment.
- **FL-4 Limits to test, not assume.** *(inference)* The incentive holds where the declarer bears the consequence (stock). It does not police cash or value taken outside the system, and it does not detect *over*-declaration; those need an independent flow (payments, a periodic count — the pawn day-end count, `PAWN_FINTECH_SPEC.md` §20.5).
- **FL-5 Ids are pseudonymous, not confidential.** Without the seed an id means nothing — real data minimisation. But ids are small sequential integers, a seed can be public (GardenWorld), and volume and timing stay visible, so flows are still sealed (CL8, §13.4). References to seed rows use the seed key (identical on every device because the base is hash-pinned); references to records created on a device use `<table>_uu` (§11.1).
- **FL-8 UPS — the Unicenta POS Strategy: ONE DocAction, at the processor (owner, 2026-10-26: *"UPS is Unicenta POS Strategy. Which we already noted prior that it does not need to handle Docaction locally as there's no need to do any posting. At server those are done to return just replenish movement. Harden the specs to grasp this UPS well as dual Docaction may results on ghost and loss of single source of truth."*).** (a) The point of action (the POS station) only DECLARES: the lines (product, qty, uom) under its ticket key POSStation/Date/Order# (§16.16a). It does NOT complete, post, reserve, or create shipments or invoices — **no DocAction on the station**; its own stock deduction is an advisory copy (FL-2). (b) The PROCESSOR (the HQ/server role) receives the declaration, authors the document, runs the DocAction **once** (Complete + posting), and returns only what the station needs: the **replenishment movement** (product, qty). (c) **Every document has exactly ONE DocAction executor, named by the plan.** No other device runs completeIt / posting for it — not even "deterministically". Reason, measured: a second run mints its own ids (1–3 generated uu per Complete, §36.1 T3(e)), its own document numbers (§36.1 T3(b)) and its own Fact_Acct lines → **GHOST records** (two shipments, two postings for one sale) and **a second source of truth** that can drift. (d) FL-2's 2026-10-25 reword ("in a mesh every member runs the same fold") covers derived VALUES that are recomputed and never stored as records of their own (a stock sum, a balance, a rank). **It never licenses running a DocAction or a posting on more than one device.** (e) The single run's consequences are not broadcast either: each other role receives only the flows the plan declares for it (the station: replenishment). ## §46 G-10 as an OSGi-style release — spec, and the dangers of the new shape (owner, 2026-10-29: *"Actually OSGi has a standard too, plugin versioning, to solve such hell that cuts across everyone. … Yes. Do you foresee any dangers? I am thinking of what scenario in this new shape can break it."*)
**Today (measured 2026-10-29):** two versioning schemes. (a) Plugins, in `erp/plugin_registry.js`: semver, mandatory `version`, an `engineVersion` gate, `requires` checked with SINGLE-comparator ranges (`*`, `=`, `>=`, `>`, `<=`, `<`), and `resolveDeps` refusing a missing dependency, a conflict or a cycle. (b) Team op shapes, in `common/comm/op_versions.js`: a per-op-type version; upcasters as SIGNED DATA; `v > appV` → PARKED `needs-upgrade`; a missing step → PARKED `needs-mapping`; **`v < min_v` → REFUSED `retired-version` (`:101`)**. And **no base-upgrade path**: changing a hashed base file forces re-founding (`W-BASE-RELEASE` out of scope, :2293).
**Spec:**
- **ONE versioning scheme** for plugins and op shapes, OSGi semantic versioning: `major.minor.micro`; a minor or micro change is backward compatible and a major is breaking; dependencies and compatibility as two-sided OSGi ranges (`[1.2,2)`). The plugin registry gains two-sided ranges, the op shapes adopt the same numbers, and one parser serves both (deletion budget: the two separate version parsers go).
- **A release** = a signed package: the Pack Out contents (dictionary / plan / translation rows), its version, its compatibility range, and `prev`, the hash of the release it follows (chained, as trusted keys and executor maps are).
- **Screens, inside Plugins & Releases**, industry words with the legacy name in brackets: **Publish schema update** (Pack Out), **Rollout** (Packages Installed: adopted by N of M devices, who is behind, why), **Trusted keys** (a chained history), **Sync rules** (Replication Strategy, read-only).

### §46.2 Module TTL: "this code has expired, check for updates" (owner, 2026-10-29: *"Thinking also the version control can set each module a TTL so it can warn user code has expired and need to check back for updates."*)
**Industry name:** an **expiry on signed metadata**: TUF puts an `expires` date on every signed role file, so that a device cut off from updates (by accident, or by someone blocking them: TUF calls it a *freeze attack*) does not keep believing it is current. **Spec:** every release and every plugin bundle carries `expires` in its signed manifest (set by the publisher, e.g. 90 days). When it passes, the device shows *"<module> <version> expired on <date>. Connect to check for updates."*: in the Team chip, in Plugins & Releases, and on the module's own screen. **The rules that keep it safe in local first:**
- **It warns; it never stops business.** A till keeps selling, and a phone keeps declaring slips, on an expired module: refusing work offline would break the immutable principle (no realtime dependency in the path). What expiry MAY hold back is publishing: an admin device on an expired release cannot publish a new one until it has synced, because it would otherwise publish on top of an out-of-date chain (D4).
- **Clock honesty (the D11 concern):** expiry is the one place a date is used, and it only raises a warning, so clock skew can only make the warning early or late, never change data. The device compares `expires` against the later of its own clock and the newest signed timestamp it has seen in the log, so winding the device clock back does not hide an expiry.
- **Renewal without a new build:** the publisher can extend `expires` with a signed renewal (the same chained statement, a new `expires`, the same contents). Devices adopt it at their next sync.
- **Witness arms:** expired → the warning text in all three places, and business still works (a till sale and a slip are accepted) · the clock set back below the newest signed timestamp → still expired · a signed renewal → the warning clears at the next sync · an admin on an expired release → publishing refused with the reason · mutant: expiry blocks a sale (must be caught).

### §46.3 The update list: a tiny signed flag list, for people to SEE, not to update blindly (owner, 2026-10-29: *"Or there is a tiny flag update list to say which is so.
