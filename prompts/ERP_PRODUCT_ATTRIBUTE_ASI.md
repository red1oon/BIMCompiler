## 4. Gap list (study 2026-10-22; legacy read at ~/idempiere-dev-setup/idempiere/org.adempiere.base/src/org/compiere/model unless noted; twin = bim-ootb main ba4ad07b)
**Plain words first.** An *attribute set* says what kind of facts a product can carry (colour, size, "has a lot number", "has a serial number", "has an expiry"). An *instance* (ASI) is one filled-in copy of that set: "Lot L-77, expires 2027-03-01". Stock, shipments, cost and matching are all keyed by product + instance, so two lots of one product are two separate stock rows and a shipment must say which one it took (the *MA* allocation lines).

**In plain language.** An *attribute* describes the **kind** of product and is shared by every unit - colour, size. In SAP, D365, ERPNext and Odoo a new attribute value normally creates a **separate variant** (its own item, its own stock count). An *instance* describes **one lot or serial** - lot number, expiry, warranty; it is a label on a physical batch, not a new product. The four big ERPs keep these as **two separate concepts** (SAP: classes/characteristics vs batch master/serial profile; D365: product dimensions vs tracking dimensions; ERPNext: Item Attribute vs Batch/Serial No; Odoo: Attributes vs Lots/Serials). iDempiere folds both into one mechanism - the Attribute Set and its Instance - so one screen (the attribute dialog) handles colour *and* lot *and* expiry, and the whole stock/shipment/cost chain is keyed by that one instance id. Everywhere, stock is counted per variant or per instance, picking follows a date rule (first-in-first-out, or earliest expiry first), and cost follows an instance only if you switch that on (D365 "financial inventory", Odoo lot valuation, SAP split valuation, iDempiere Batch/Lot costing level). **What would bite a twin user first** (§4): there is no dialog to create the lot/serial at all (AS-1), then "mandatory" is never enforced (AS-2: the order check reads a column that does not exist), then shipments ignore expiry dates (AS-3).
