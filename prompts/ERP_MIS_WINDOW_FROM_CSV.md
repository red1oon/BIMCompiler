## 1. The idea in one paragraph
A person keeps a small table in a spreadsheet: assets, visitors, training records. Today they would need a developer to get a screen for it. Here they save the sheet's description as `asset.csv`, type one line, and the ERP gains a real window: menu entry, grid, form, find, export, roles, history. The same engine that runs Sales Order runs it, with no code written for it. Then they load their rows from a second CSV, and read them back as CSV. That is an MIS built by its user.

## 3. The design (advised; §6 holds the three points the owner may overrule)
### 3.1 The lines a person types
```
erp.add_window file=asset.csv                 -- the owner's "Add window = asset.csv"
erp.add_window file=maintenance.csv master=AST_Asset
erp.load file=asset_rows.csv table=AST_Asset  -- create rows from a natural sheet
erp.load file=asset_rows.csv table=AST_Asset update=Y
erp.list kind=AST_Asset --csv --out assets.csv   -- NEURO §R.V item 5
erp.remove_window table=AST_Asset
```
- A file name without a path is looked for **in the folder of the script being run** (a single typed line: the current folder). A path that leaves that folder is refused. The door journals the file's sha256 with the line, so a replay with a changed file is detected and refused.
- The table name is the file name without `.csv`, unless `table=` is given. It must carry a prefix that is not a core one (Ninja's rule: a 2 to 4 letter module prefix and `_`); a name that matches an existing core table is refused.
- Harm: `erp.add_window` and `erp.remove_window` change the dictionary: harm `writes`, plus a new flag `"dictionary": true` in the vocabulary entry so an AI's call is always held as a claim and the role must hold the System Administrator's grant (as legacy: these are System-level windows). `erp.load` is `writes`. `erp.list` is `read`.

### 3.2 The properties CSV (one file = one table; one row = one column)
Header row, then one row per column. Only `Column` is required; an empty cell takes the Ninja default.
```
Column,Type,Length,Mandatory,Identifier,Default,List,Lookup,Callout,Help
Name,String,60,Y,Y,,,,,
PurchaseDate,Date,,,,,,,,When it was bought
Cost,Amount,,,,,,,,
Condition,List,,,,GOOD,"GOOD=Good,FAIR=Fair,POOR=Poor",,,
C_BPartner_ID,,,,,,,,,Supplier
IsInsured,,,,,,,,,
```
- `Type` takes the Ninja words (String, Quantity, Amount, YesNo, Date, DateTime, Text, List) or their one-letter prefix. Empty: Ninja's own rule by name (`Is*` = YesNo, `*_ID` = lookup, else String). An unknown word is **refused naming it** (the parser's "String + warning" is kept for workbooks, but a typed CSV fails loudly).
- The standard columns (`<Table>_ID`, `_UU`, client, org, IsActive, Created/By, Updated/By) are added as Ninja adds them and must not be listed; listing one is refused.
- `Length`, `Mandatory`, `Identifier`, `Default`, `Help` are AD_Column's own properties, which the Ninja grammar has no token for. They are dictionary data, not new behaviour: the model layer and the window already read them. Each one is offered only after M0 proves the engine honours it on a staged table.
- Table-level facts are inputs on the line, not rows: `master=` (the table becomes a detail tab of that window), `workflow=Y` (Ninja's DocStatus / DocAction / Processed / DocumentNo / IsApproved set), `name=` (the window's label; default: the table name with `_` as spaces), `menu=` (parent menu node; default: one summary node named after the prefix).
- One reader turns the CSV into **the same model object `ninja_model.parseSheet` returns**; from there the path is Ninja's own (`stageModels`). No second staging engine (AD-LAYER LAW 5).

### 3.3 Where the new window lives
- **At the door (CLI, AI):** the dictionary rows are written as op-log ops through `persistGroup` (the path `erp.complete` already uses), so they replay on every boot. The data table is not an op: a generic boot step creates the physical table for any active AD_Table that has none, from its AD_Column rows (the rule `ad_import_tables.js` applies by hand for four `I_*` tables; the generic step can then retire that hand-kept DDL, counted in the deletion budget).
- **In the browser:** the same model is emitted as a `.foldbundle` (`ninja_bundle.emitBundleSource`) next to the CSV, and the Create face accepts `.csv` as it accepts `.xlsx`. One model, two hosts, compared by a witness.
- The CLI's op-log and the browser's store are two stores today. This file does not merge them; it makes both reach the same rows from the same CSV and proves it.

**12.10 Spec: do not replay the whole op-log on every line (idea 8; before the witness and the code):**
- **Measured (§12.2 E8):** after the 19-table workbook every later line costs 0.72 to 0.87 s against 0.34 s, because its 718 ops are applied again on each start.
- **Rule:** the result of applying a PREFIX of the op-log to the patched seed is kept as an image, as the patched seed itself already is (`ERP_SNAPSHOT`, §0.16). The image is used only when the op-log still begins with exactly those bytes (sha256 of the prefix) and the seed key is the same; then only the ops after the prefix are applied. An op-log that was edited, shortened or replaced gives a full replay. A new image is written when the ops applied after the image reach a threshold (`ERP_OPIMAGE_MIN`, default 200: about 0.1 s of replay by the measured rate); `ERP_OPIMAGE=off` and `ERP_SNAPSHOT=off` switch it off. One image per op-log file, in the snapshot folder; an image whose op-log file is gone is deleted when another is written (a temp op-log must not leave 27 MB behind).
- **Witness W-ERP-OPIMAGE** (`common/door/tests/witness_erp_opimage.js`; falsifiers `ERP_BREAK=staleimage`, `noimage`): **G1 same answers:** on an op-log of a staged workbook plus records, a set of read lines (every staged kind listed, described and one read) answers byte for byte the same with the image and with `ERP_OPIMAGE=off` (X of N lines, N from the dictionary). **G2 same data:** every dictionary table and every staged table holds the same rows by both routes (a hash per table, T of T). **G3 it follows the log:** a line appended after the image is seen; an op-log whose earlier line is changed gives the changed result (the image is not used). `staleimage` (the prefix is not checked) must FAIL it. **G4 it is used and it is cheaper:** the boot line says the image was hit and how many ops were applied; wall time of a later line with and without, logged; `noimage` must FAIL the "hit" claim. **G5 housekeeping:** an image whose op-log was deleted is gone after the next image is written; no temp file is left. INCONCLUSIVE when the op-log is below the threshold.
- **RESULT §12.10 (2026-11-14, bim-ootb PR #2993 merged; logs read):** W-ERP-OPIMAGE **5 pass / 0 fail / 0 inconclusive** on a 148-op log (threshold set to 50 for the run). **12.11 Spec: `ninja.rollback` and `ninja.export` (ideas 3 and 2; 2026-11-14, before the witness and the code; parity read from legacy `org.ninja.process.DeleteModel` and `NinjaExporter`):**
*Legacy facts read (re-read from the sources, not recalled):* **DeleteModel** refuses a table that holds rows (`"ERROR <table> HAS DATA! **The lines:** `ninja.rollback bundle=<name> [dry=Y]` and `ninja.export (bundle=<name> | window=<name or id> | table=<name>) file=<name>.xlsx`.
**Rules (each is a claim; each names the issue it proves):**
- **R1 (undo is complete)** after `ninja.exec` then `ninja.rollback bundle=`, no window, tab, field, column, table or menu entry of the bundle is active, and the bundle's summary node is off; the dictionary outside the bundle is untouched (counts of active rows of every other AD row equal their count before the exec). *Issue: a half-undone workbook leaves windows with no table.*
- **R2 (parity: data blocks it)** a bundle table that holds a row refuses the whole line, names the table and its row count, and writes nothing (op count unmoved); `dry=Y` names the same and writes nothing. *Issue: a rollback that deletes people's records.*
- **R3 (only what the bundle made)** a table that came with the system (outside the Ninja range) loses only the Ninja-range columns and the tab the bundle added (a tab on Business Partner goes, Business Partner stays); an unknown bundle is refused (`no staged bundle is named`); with no bundle named the line is refused and never means "all".
- **R4 (it is an op, not a patch)** the rollback is one group of `CRUD_UPDATE isactive Y->N` ops in the log, so it replays after a restart and the door's undo of that group brings the bundle back. *Issue: a change that exists only in memory.*
- **R5 (twice is nothing, and a re-run works)** a second rollback writes 0 ops and says so; `ninja.exec` of the same workbook after a rollback stages it again (the bundle is whole and active), with the data sheets loaded.
- **E1 (the model leaves intact)** `ninja.export bundle=` writes a workbook whose model sheet, read back by the same parser `ninja.exec` uses, gives the same tables, Master links, column names, reference types and list values as the sheet that made the bundle (compared field by field). *Issue: the file says something the system does not hold.*
- **E2 (the round trip)** the exported file run by `ninja.exec` on a fresh door makes the same shape (tables, detail tabs, columns, lists); and after an EDIT of the exported sheet (a column added) the run makes that column. *Issue: "edit the sheet and run it again" is the promise of the line.*
- **E3 (no rows, no overwrite, no "everything")** the file holds the model only (stated in the answer, as legacy writes the model only); a file that already exists is refused (never overwritten); no selector is refused with legacy's rule; a table that came with the system is refused (its model is the system's own).
**Falsifiers:** `NINJAROLL_BREAK=keepmenu` (leaves the menu entry on: must FAIL R1), `nodatacheck` (must FAIL R2), `blanket` (rolls back every Ninja-range table: must FAIL R3), `NINJAEXPORT_BREAK=nomaster` (must FAIL E1, E2), `nolists` (must FAIL E1). A claim with nothing to judge says INCONCLUSIVE.
