**What it is.** `modeller/tools/model_session.js` starts ONE headless Modeller page on the CPU (no GPU; `--use-angle=swiftshader`), a local port on 127.0.0.1 with a one-time token and a state file `.model_session.json` in the folder the door line runs from. Each door line is its own process that sends one command to that page, so `model.open`, `model.convert`, `model.addbay` act on what the line before left. The page does all the work with its own functions (the DXF import, Convert, Add a bay: `dxf_import_ui.js`, `bay_add.js`, §D89/§D90); the driver presses what a person presses and reads the page's own answers. Nothing is saved: `model.close` drops the model.
**The lines (harm `trial`, human + ai):** `model.open sheets=<folder|a.dxf,b.dxf> [type="Farming Shed"]` · `model.convert` · `model.addbay end=high|low` · `model.undo` · `model.close`. ## §S2 Spec: `model.save` and save on close (2026-11-15; owner: "57s just to save?! Then a manual save /s or save on close then", "you work it out")
**Read first (bim-ootb `modeller/modeller.html` L3454-3557, `save_catalog.js`):** the page's Save (`runSave`) is (1) the clash gate `SdgGate.evaluate` over every element, (2) one auto-heal pass and a second gate when the first finds RED, (3) the fold `Bonsai.exportDb` (the native `.db`, the same writer as Export), (4) `SaveCatalog.pushVersion` into the browser's IndexedDB. The 57 s of the older note (`prompts/archive/FRONTEND_LANE_MASTER.md` L268) was Save **with auto-heal on a 35,000-element model** (two full gates + the fold), never profiled; the headless session's IndexedDB lives in a throw-away profile, so step 4 alone keeps nothing once the session closes.
**Decision (owner):** a manual save and a save on close; no autosave.
**The lines:** `model.save [file=<name>.db]` presses the page's Save; a RED clash blocks it as on screen (the answer names the clash, nothing written); when clean, the `.db` the Save folded is written to `file` (in the folder the line runs from; a file that exists is replaced only by a save of this same session). `model.open … [file=<name>.db]` names the save file up front. `model.close` saves first when the model changed since the last save and a file is known; with changes and no file it is REFUSED ("unsaved changes: model.save file=… or model.close discard=Y"); `discard=Y` drops them on purpose.
**Profile (in every save answer):** `ms` per phase: gate, heal (+ re-gate), fold, catalog, file write; the element count. Phase times are read from the page's own § lines (`§SAVE_GATE`, `§SAVE_CLEAN`/`§SAVE_BLOCKED`, `§SAVE_SNAPSHOT`) as they arrive.
**Claims (W-MODEL-SAVE):** M1 a clean save writes a `.db` whose bytes equal the page's own export (sha256 of the catalog's latest version = sha256 of the file) and the answer's phase times add up to its total within the driver's own overhead; M2 save before anything changed is refused ("author something first", the page's own words); M3 close with unsaved changes and no file is refused and the session stays open; `discard=Y` closes; M4 close with a known file and unsaved changes writes the file first (its sha256 = the page's latest version) and then closes; close right after a save writes nothing new; M5 a file outside the folder is refused.
**Falsifiers:** `MODELSES_BREAK=nofile` (the bytes are not written: must FAIL M1, M4), `closedrops` (close never saves: must FAIL M4).
**§S2 RESULT (2026-11-15, bim-ootb #3051 `feat/model-save`):** W-MODEL-SAVE **7/0** (M1-M5, M3b, M4b); falsifiers `nofile` FAILs M1+M4, `closedrops` FAILs M3+M4+M3b (logs `modeller/tests/logs/model_save*.log`). W-MODEL-SESSION 10/0 after its closes became `model.close discard=Y` (a plain close no longer drops unsaved work: the owner's save-on-close); its falsifiers fail as before (notype S2b S3a-c S5; stale S3a-c; nounder S3b). **Measured, the Shed (444 elements, this machine, CPU):** a save is 0.42-0.65 s in four runs: gate 6-21 ms, heal ~0, fold + catalog 129-322 ms, read-back 73-92 ms, file write 4-5 ms; the `.db` is 1,298,432 bytes, `PRAGMA integrity_check` ok, its sha256 = the page's catalog version. The 57 s of the old note is the 35,000-element Save with auto-heal; a Save on a model of that size is still not measured here.
**Finding (reported to the Modeller lane, not fixed here):** the Save gate's verdict on an added bay depends on the order of saves: convert → addbay → save is CLEAN, convert → save → addbay → save is BLOCKED by 54 RED clashes (36 orange), while `model.addbay`'s own gate says clean both times. `runSave` judges `SdgGate.evaluate(before=__saveGateBaseline, after, moved)`: the baseline rolls forward on each save, so with no save in between the bay's copies are not among the moved and are not judged (a scope-blind verdict, WITNESS_INTERFACE_FRAMEWORK); after a save they are, and 54 clash. Which verdict is right (does the bay really clash?) is the Modeller lane's question.
