    Fast Script ユーザーガイド¶

    BIM と ERP のアプリに、短いコマンドをひとつずつ、またはファイルに書いた数行を渡すと、アプリ自身の答えが返ってきます。同じ行が、端末を使うあなたにも AI にも使えます。

    これはひとつのドアの案内です。ドアとは、アプリの手前に置かれた小さなスクリプトエンジンです。たとえばmodeller.lines building=HospitalGarageのような行を書きます。ドアはその行を読み、決まった動詞の一覧と照らし合わせて確認し、アプリ自身のコードを呼び出して、確認されなかった項目と一緒に答えを返します。ドアの中に AI はありません。

    図を左から右へ読んでください。

    1. アクター。 行を送る主体と、行が届く経路です。現在は、ツール接続を通した AI か、端末の前にいる人です。メールボックス、電話、機器は計画中で、まだ作られていません。
    2. チャネル：動詞。 アクターが言えることすべての一覧です。各動詞には、わかりやすい説明、入力、そして影響クラス（harm）があります。一覧全体は下記にあります。
    3. ひとつのドア：スクリプトエンジン。 行を解析し、入力を確認し、その行を依頼した主体に結び付け、アプリを呼び出して、返信します。どのアクターも同じドアを通るので、同じ行は同じ答えになります。
    4. エンジン：アプリ。 判断するのはアプリ自身のチェックです。新しい問題を加える変更は取り消され、その理由が返されます。

    良い答えが意味しないこと

    問題のない答えは、安全、適合、良好のいずれも意味しません。各答えには確認されなかった項目が並び、確認されないことにもう一度まとめてあります。最終判断は構造技術者が行います。

    AI を使う新規の方へ。 AI をドアにつなぐ方法は、AI Proposer ガイドにあります。このページは、ご自身で書くコマンドやスクリプトと、返ってくる答えの読み方のためのものです。

    red1 早わかり¶

    red1は近道の入口で、BIM と ERP のアプリに対するひとつのプロンプトです。短い言葉はそれぞれ、実行するドアの完全な行を（→の後に）表示するので、使いながら長い形を覚えられます。red1 の詳しい説明は、このページの終わり近くにあります。

    入力 できること
    red1 red1>プロンプトを開く（node common/door/red1.js、または一度npm linkした後はred1）
    cd Duplex · cd Element · cd Order · cd .. · pwd 建物、その種類、または ERP の種類へ移動する。戻る。今いる場所を表示する
    count · ls · group storey · sum <column> · cat <id> ここで、数える、一覧する、まとめる、合計する、ひとつのレコードを表示する
    ls element_name=*bath* ワイルドカードで検索：*は任意の文字列、?は一文字、[abc]はそのうちのひとつ
    clash ARC MEP · then ls · ls *Bath* 衝突をファネルで描く。その行。一致する行
    clash 建物の分野のメニューが開く：矢印キーまたは数字キー、そして Return
    next <number> · do complete <number> 伝票が今できること。それを実行する
    menu · help · help verbs · exit ERP メニュー。言葉の一覧。ドアのすべての動詞。終了
    red1 'cd Duplex; count' 同じ言葉をスクリプトから、一回だけ実行

    ドアを入手する¶

    Node 18 以上が必要です。この手順は Node 18.19 で実行しました。

    Modeller の動詞には六つのファイルが必要です。 空のフォルダを作り、ブラウザエンジンをインストールして、ファイルをダウンロードします。

    mkdir fastscript && cd fastscript
npm init -y
npm install puppeteer@24
curl -O https://red1oon.github.io/bim-ootb/modeller/tools/edit_cli.js
curl -O https://red1oon.github.io/bim-ootb/modeller/tools/bim_mcp.js
curl -O https://red1oon.github.io/bim-ootb/common/door/door.js
curl -O https://red1oon.github.io/bim-ootb/common/door/verbs.json
curl -O https://red1oon.github.io/bim-ootb/common/door/msg_core.js
curl -O https://red1oon.github.io/bim-ootb/common/door/vocab/messages.json

    六つとも同じフォルダに置いてください。door.jsはverbs.jsonから動詞の一覧を、messages.jsonから（msg_core.jsを通して）メッセージを読み、edit_cli.jsを実行し、これがライブの Modeller ページをウィンドウなしで開きます。ファイルが足りないと、ドアはどれが足りないかを知らせ、そのcurlの行を表示します。bim_mcp.jsは AI をつなぐときだけ使います。このページのコマンドでは使いません。

    Viewer、オブジェクト、スケジュールの動詞には、完全なチェックアウトが必要です。 これらは六つのファイルには含まれません。bim-ootbリポジトリ全体（git clone https://github.com/red1oon/bim-ootb）を取得し、node door.jsの代わりに、その最上位のフォルダからnode common/door/door.jsを実行してください。動詞の表には、各動詞がどちらを必要とするかが書かれています。Viewer 用の一ファイル版ダウンロードは、まだ作られていません。

    最初のコマンド¶

    一行に動詞をひとつ、key=valueの組を、=の前後に空白を入れずに書きます。HospitalGarage にグリッドを尋ねます。

    Modeller と建物を開くので、10〜40秒かかります。表示されるのは、エンベロープと呼ぶ一行の JSON です。ここでは先頭だけを示します。グリッドの線は収まりきらないほど多いためです。答えはアプリ自身のもので、answerの中にそのまま入っています。ここでは、建物自身のグリッド上で、gx5が 145.987 m、gx6が 157.163 m にあります。statusはokです。

    「request」はどこから来るのか

    どの行にもリクエスト ID（"request":"d-…"）が付き、実行する前にジャーナルへ書き込まれます。保存先は~/.cache/bim_door/journal.jsonlです。同じ ID を二度送ると最初の答えが返るので、再試行で変更が繰り返されることはありません。ドアはまた、エラーストリームに§DOOR …の行をひとつ出力します。このガイドでは標準出力だけを示します。

    ひとつの動詞でリクエスト全体を¶

    「gx5 と gx6 の間のベイ（柱の間の区画）を幅 13 m にする」のようなリクエストには、いくつかの手順があります。グリッドを読み、動かす量を求め、ずらしを試すことです。動詞modeller.widen_bayは、この三つをすべて行います。入力は二本の線と、希望する幅です。

    $ node door.js 'modeller.widen_bay building=HospitalGarage from=gx5 to=gx6 target=13' > widen.json; echo "exit $?"
exit 3

    終了コードが最初の答えです。0は ok、3はアプリが単純な「はい」ではない答えを返したこと（拒否、保留、または結論不能）、1はエラー、2は間違ったコマンドを意味します。次にファイルの中を見ましょう。最初にリクエスト全体があり、続いて二つの手順が、それぞれ自分のエンベロープとともに並びます。

    $ grep -o '"request":"[^"]*","verb":"[^"]*","actor":"[^"]*","status":"[^"]*"' widen.json
"request":"d-mwiqhyza-3186904-1","verb":"modeller.widen_bay","actor":"human","status":"refused"
"request":"d-mwiqhyza-3186904-1.1","verb":"modeller.lines","actor":"human","status":"ok"
"request":"d-mwiqhyza-3186904-1.2","verb":"modeller.try_shift","actor":"human","status":"refused"

    最初の手順でグリッドを読みました。今のベイは次のとおりです。

    $ grep -o '"id":"gx[56]","axis":"x","pos":[0-9.]*' widen.json
"id":"gx5","axis":"x","pos":145.987
"id":"gx6","axis":"x","pos":157.163

    つまり、ベイは 157.163 − 145.987 = 11.176 m です。13 m にするには、線gx6とそれ以降のすべての線を 1.824 m 動かす必要があります。ドアがそれを計算し、二番目の手順に渡しました。

    $ grep -o '"move":[0-9.]*' widen.json | head -1
"move":1.824

    アプリはずらしを試し、確認して、止めました。

    $ grep -o '"why":"[^"]*"' widen.json | tail -1
"why":"line 2 (modeller.try_shift): stopped: Beam spans over limit: 91 -> 92 (limit 12 m, RC); bay gx5-gx6 newly over the limit: 13 m"

    変更は行われ、判定され、取り消されました。保存されるものは何もありません。止めた根拠の数字は、アプリのレポートにあります。

    $ grep -o '"bay":"gx5-gx6"[^}]*' widen.json
"bay":"gx5-gx6","before":11.176,"after":13,"newly_over":true

    ベイは 11.176 m から 13 m になり、この建物のコンクリート梁の上限 12 m を超えました（limitとmaterialは建物自身から取得します）。これが Garage のリクエストの顛末のすべてです。13 m のベイには、もう一本の柱の列が必要です。

    スクリプト：複数の行、名前付きの結果¶

    スクリプトは、一行にひとつのコマンドを書いたテキストファイルです。行は名前と=で始めることができ、その答えを下の行のために取っておけます。--以降はコメントです。次をbay.doorとして保存してください。

    -- read the grid, then widen the bay between gx5 and gx6 to exactly 12 m
lines = modeller.lines building=HospitalGarage
modeller.try_shift building=HospitalGarage line=gx6 move={12 - (lines.model.lines[gx6].pos - lines.model.lines[gx5].pos)}

    --scriptで実行します。

    $ node door.js --script bay.door > bay.json; echo "exit $?"
exit 0

    { }の中のテキストは算術式です。数、+ - * /、かっこ、名前付きの結果のフィールドを使えます。lines.model.lines[gx6].posは、「linesという名前の答えの、modelの下にある、linesのうち id がgx6の項目の、pos」という意味です。動詞が宣言したフィールドだけを読めます。それ以外の名前はエラーになり、その旨が表示されます。

    算術は浮動小数点ではなく、正確な十進数で行います。浮動小数点を使うコンピュータでは、12 - 11.176 = 0.8239999999999998となります。ドアでは次のようになります。

    $ grep -o '"change":{"kind":"[^"]*","grid":"[^"]*","through":"[^"]*","lines":[0-9]*,"delta":[0-9.]*' bay.json
"change":{"kind":"block-shift","grid":"gx6","through":"gx16","lines":11,"delta":0.824

    スクリプトは上から下へ実行され、ok でない最初の行で止まります。ここでは二つともokと答えます。

    $ grep -o '"request":"[^"]*","verb":"[^"]*","actor":"[^"]*","status":"[^"]*"' bay.json
"request":"d-mwiqis8z-3188092-2","verb":"modeller.lines","actor":"human","status":"ok"
"request":"d-mwiqj50r-3188092-3","verb":"modeller.try_shift","actor":"human","status":"ok"

    ちょうど 12 m では、アプリは新しい問題を見つけません。上限を超える梁スパンの数は、変わらないままです。

    $ grep -o '"label":"Beam spans over limit","scope":"[^"]*","state":"JUDGED","before":[0-9]*,"after":[0-9]*,"delta":[0-9]*' bay.json
"label":"Beam spans over limit","scope":"228 walked girders, RC (mixed building)","state":"JUDGED","before":91,"after":91,"delta":0

    このように、同じ建物でも、13 m を求めると止められ、12 m を求めるとそのまま成り立ちます。okは建物が良いという約束ではありません。同じ確認されないことの一覧が当てはまります。

    行の文法¶

    部分 規則
    コマンド app.verb key=value key=value、一行にひとつ
    空白を含む値 二重引用符で囲む：text="a note"
    名前付きの結果 name = app.verb …。後の行はname.fieldを読む
    算術 { … }の中に、数、+ - * /、かっこ、結果のフィールド。正確な十進数
    コメント --とその行の残り
    単位 行には書かない。動詞が、メートル、時間、日のいずれかを決める
    それ以外 コマンドではない。アクションとしてではなく、質問として返ってくる

    最後の行は意図的です。どの動詞にも一致しないテキストは、決して推測されません。

    answer アプリ自身の答え。そのまま

    申請（claim）とは何か¶

    各動詞には影響クラス（harm class）があります。read（何も変えない）、trial（使い捨てのコピーに対して行う変更で、判定され、保存されない）、writes、posts、sendsのいずれかです。このクラスは動詞の一覧に一度だけ書かれているので、どのアクターも言いくるめて回避することはできません。

    各アクターには証明があります。端末の前にいる人は、すべてのクラスで信頼されます。AI が信頼されるのはreadとtrialだけです。見ることと試すことはできますが、AI からのwrites、posts、sendsの動詞は、上のobject.updateの行のように、申請として保留されます。知らない送信者からのメールのように、証明がまったくないアクターは、読むことだけができます。

    $ node door.js --actor email --request mail-0 'modeller.try_shift building=HospitalGarage line=gx6 move=1.824'
{"request":"mail-0","verb":"modeller.try_shift","actor":"email","status":"claim","answer":null,"why":"actor email has proof \"none\", which allows read verbs; modeller.try_shift is trial. Held as a claim, not run. A person confirms it with: door.js --confirm mail-0","notChecked":[],"ops":[],"next":[],"ms":7}

    保留中の申請は、実行されず、キューに入らず、失われもしません。リクエスト ID の下で、ジャーナルに残ります。ドアは、誰かの代わりに何かを承認することはありません。

    申請を承認する¶

    人は、保留された申請をリクエスト ID を指定して通します。そのため、実行される行は、提案されたとおりの行になります。誰も打ち直しません。ここでは、メールが試行の移動を求め、保留されます。

    $ node door.js --journal claims.jsonl --actor email --request mail-1 'modeller.try_shift building=HospitalGarage line=gx6 move=0.824'
{"request":"mail-1","verb":"modeller.try_shift","actor":"email","status":"claim","answer":null,"why":"actor email has proof \"none\", which allows read verbs; modeller.try_shift is trial. Held as a claim, not run. A person confirms it with: door.js --confirm mail-1","notChecked":[],"ops":[],"next":[],"ms":7}

    --claimsは保留中のものを一覧します。

    $ node door.js --journal claims.jsonl --claims | grep -o '"actor":"[a-z]*","line":"[^"]*","verb":"[^"]*","harm":"[a-z]*"'
"actor":"email","line":"modeller.try_shift building=HospitalGarage line=gx6 move=0.824","verb":"modeller.try_shift","harm":"trial"

    --confirmは記録された行を、あなたとして、一度だけ実行します。

    $ node door.js --journal claims.jsonl --confirm mail-1
{"request":"mail-1#confirmed","verb":"modeller.try_shift","actor":"human","status":"ok","answer":{"ok":true,"building":"HospitalGarage","edits":[{"tag":"EDIT_REPORT","version":1,"change":{"kind":"bloc…

    返信は通常のものですが、承認した申請の名前が入っています。もう一度頼んでも何も実行されません。ドアは自分の記録から答えます。

    $ node door.js --journal claims.jsonl --confirm mail-1 | grep -o '"confirms":"[^"]*"'
"confirms":"mail-1"

    三つの規則が成り立ちます。承認できるのは端末の前にいる人だけで、--actor ai --confirm …は拒否され、申請は保留のままです。アプリは承認の時点でも判断するので、提案されてから間違ったものになった行は、アプリの理由とともに拒否されます。そして AI のツール接続には、承認コマンドそのものがありません。

    これが証明しないこと。 ドアは、ローカルの端末の前にいる人を信頼します。お使いのマシンでシェルコマンドの実行を許された AI は、あなたとして行を入力できるのと同じように、--confirmを自分で入力できてしまいます。それが問題になる場合は、AI のアクセスをツール接続だけにとどめてください。

    自分のスクリプトからドアを使う¶

    上のすべてはdoor.jsで、AI 接続が使うものと同じファイルです。ご自分のプログラムからは、これをコマンドとして呼び出し、その JSON を読みます。終了コード（0、3、1、2）が、答えと問題のどちらを読むべきかを示し、statusがどちらかを示します。--actor humanが既定です。--actor aiにすると、ドアはその行を AI のものとして扱います。

    ウォーカーが配置するもの：modeller.walk¶

    Modeller には、ひとつの分野（discipline）の取り付け部品（スプリンクラー、照明、コンセント）を、実際の建物から測ったルールで配置するウォーカーがあります。modeller.walkはそのドライランで、ウォーカーが何を配置するかを答え、何も変えません。モデルのファイルは、実行の後もバイト単位で同じで、答えもそう述べます。チェックアウトが必要です。完全な返信は長いので、ここでは主な数値を示します。

    $ node common/door/door.js 'modeller.walk building=Duplex discipline=FP' | grep -o '"rules":"[^"]*"\|"count":[0-9]*,"placed":[0-9]*,"provisional":[0-9]*\|"byClass":{[^}]*}\|"modelUnchanged":[a-z]*'
"rules":"duplex_rules.db"
"count":46,"placed":0,"provisional":46
"byClass":{"IfcFireSuppressionTerminal":45,"IfcAlarm":1}
"modelUnchanged":true

    countは、ウォークが配置するすべてです。provisionalは、ウォーカー自身が「最終ではない」とする位置で、たとえば上に天井が見つからない取り付け部品です。rulesは、建物の種別が使うルールセットです。住宅は住宅用ルールを使います。何も配置しないウォークは、ウォーカーの理由とともにinconclusiveと答えます。

    行と行の間で Modeller を開いたままにする：model.open、model.convert、model.addbay、model.undo、model.save、model.close¶

    これらの行は、バックグラウンドで開いたままにしてあるひとつの Modeller ページを操作します（画面なし、CPU 上、グラフィックスカードなし）。そのため、各行は直前の行が残したものに対して働きます。model.open sheets=<folder or a.dxf,b.dxf> type="Farming Shed"は 2D のシートを開き、model.convertは 3D モデルを作り（ページ自身の Convert）、model.addbay end=high|lowは、同じ形のベイが繰り返す建物のその端にベイをひとつ加え、model.undoは直前の変更を戻し、model.closeはページを止めます。作業はすべてページ自身の関数が行います。行は人が押すものを押し、ページ自身の答えを表示します。モデルは保存するまでそのページの中にあります。model.saveはこのフォルダの.dbファイルに書き込み、model.closeは、モデルが変わっていて保存先のファイルがわかっているとき、先に保存します。これらにはbim-ootbのチェックアウトが必要で、実行するフォルダがセッションを保持します（ファイル.model_session.json。ポートはこのマシンだけで待ち受け、すべてのリクエストに一回限りのトークンが付きます）。

    出会う規則：model.openより前の行は拒否されます（"no session: model.open first"）。二回目のmodel.open、二回目のmodel.convert、Convert より前のmodel.addbayも同じです。ベイが提供されるのは、建物の種類がそれを宣言しているときだけです（Farming Shed は宣言しています）。type=がないとベイは拒否され、その種類にはルールの宣言がないと告げられます。シートには印（マーキング）が付いていなければなりません。図面の素のシートは関門を通りません。各行は数秒かかります（ここでは、開くのに約 6 秒、変換に 3 秒、ベイに 3 秒。もっと大きなシート一式では、変換に最長 15 秒かかりました）。保存： ファイルは一度だけ、model.open … file=shed.dbか最初のmodel.save file=shed.dbで指定します。保存はページ自身の Save を実行します。最初に衝突チェックが行われ（赤（RED）の衝突があると、画面上と同じく保存は止まり、何も書き込まれません）、そのあとモデルがネイティブの.dbとして書き込まれます。この小屋では保存に約半秒かかり、答えには各手順の時間が示されます。未保存の変更があってファイルがない状態のmodel.closeは拒否され、セッションは開いたままです。保存するか、model.close discard=Yで意図的に変更を捨ててください。何も作る前の保存は、ページ自身の言葉で拒否されます。

    一覧、合計、グループ化：erp.list、erp.sum、erp.group¶

    countは「いくつあるか」に答えます。読み取り専用の動詞がさらに三つあり、「どれか」「いくらか」「それぞれいくつか」に答えます。ERP の辞書にあるどの種類にも使えます（建物のモデルには、同じ三つがobject.list、object.sum、object.groupとしてあります）。チェックアウトが必要です。

    erp.listは行を表示します。列、フィルタ、並べ替えのすべてが辞書に照らして確認されるので、間違った名前はエラーになり、本当の名前が一覧されます。column=valueを加えると一覧を絞り込めます。limitで別の指定をしない限り、一覧は最大 50 行を表示し（最大 1000 まで）、答えには必ず合計が付くので、短い一覧が全体と取り違えられることはありません。長い一覧はoffsetでページを送ります。

80001       CO         100.7
800002      CO         2160
shown 3 of 14

    erp.sumは数値の列を正確に合計します。小数は小数のまま加算され、浮動小数点にはならないので、金額がずれません。erp.groupは、列の値ごとにレコードを数え、多いものから順に並べます。

n: 14

population: 44
verdict: OK
summary: 19505.9 = sum of GrandTotal over 14 Order

    $ node common/door/door.js --list 'erp.group kind=Order by=DocStatus'

CO         14
DR         6
CL         2
shown 4 of 4

    レコードがまったくない種類は、0や空の一覧とは答えません。何も判定していないので、inconclusiveと答えます。

    どのテーブルでも使う：mis.*の動詞¶

    MIS が土台です。ERP は、MIS に伝票の一生を足したものです。 レコードの一覧、読み取り、作成、変更、削除、読み込みは、辞書のどのテーブルでも同じです。顧客でも、製品でも、ご自分で作ったテーブルでも変わりません。これらの動詞はmis.*と呼ばれます。伝票だけが持つもの（完了、無効化、クローズ、取り消し）はerp.*のままです。古い名前のerp.list、erp.read、erp.describe、erp.sum、erp.group、erp.newも引き続き使えます。それぞれがmis.*の動詞の古い名前で、同じ答えを返すので、以前に書いたスクリプトは変更不要です。

    書き込むmis.*の動詞はすべて、ERP 自身のウィンドウと同じことを行います。足もとのデータベースを直接編集することはありません。既定値とコールアウトが働き、チェックが働き、拒否には理由が付き、何かが拒否されたときは何も書き込まれません。

    ロールとしてレコードを見る・変更する¶

    どのmis.*の動詞もrole=を受け付けます。ERP のロールの id です。ロールがなければ何もフィルタされません： すべてのクライアントのすべてのレコードが見えます。ロールを指定すると、そのロールが付与されているウィンドウで得られるものが得られます。つまり、そのロール自身のクライアントと組織のレコードで、しかもアクセス行が許すレコードと列だけです。合計も、それらのレコードだけを数えます。ロールは行の中に明記します。サインインではありません。

    $ for r in '' ' role=103' ' role=12000'; do BIM_OBJECT_OPLOG=/tmp/fast_guide_mis.ops node common/door/door.js --list "mis.sum kind=C_Order column=GrandTotal$r" | grep -E '^(n|sum):' | tr '\n' ' '; echo; done

n: 8 sum: 9914.07 
n: 27 sum: 55108.62

    まだ判定されない規則が五つあり、そのひとつを使うロールは、半端に確認されるのではなく拒否されます。レコードの個人ロック、テーブルの検証ルール、組織がユーザーから決まるロール、組織ツリーの要約組織を持つロール、そして「従属エンティティ」のレコードアクセスです。mis.loadはロールを受け付けません。

    普通の CSV からひとつのテーブル：ninja.exec file=<Table>.csv¶

    ワークブックの代わりの.csvは、ヘッダーがモデルになるひとつのテーブルで、古い Ninja が読むのと同じやり方で読まれます。テーブルはファイルの名前です（table=で別の名前を指定できます）。各ヘッダーのセルは、名前から型を決められ、最初に当てはまる規則が使われます。Dateを含む → 日付、Qty → 数量、Amount → 金額、IsまたはInで始まる → Yes/No（したがってIncomeも、古い Ninja と同じく Yes/No になります）、_IDで終わる → ルックアップで、そのセルはレコードの Name、=と/を含む（Plan=Basic/Gold） → 一覧、それ以外 → テキスト。C_BPartner_ID>ValueやCode=Xのようなセルは、>や=の前の列を作ります。行がレコードです。テーブルとその行は一緒に作られます。ひとつでも読み込めない行があれば、何も作られず、答えにその行が挙がります。最初の二つの列がすでにある行は読み飛ばされるので、同じファイルをもう一度実行しても何も書き込まれず、行が増えたファイルでは新しい行だけが加わります。すでにあるテーブルに対しては、ファイルは行を加えるだけで、そのテーブルの列ではないヘッダーは拒否されます。

    バンドルを元に戻す、ワークブックとして書き戻す：ninja.rollback、ninja.export¶

    二つの行で、ワークブックの輪が閉じます。ninja.rollback bundle=<name>は、ひとつのワークブックが作ったすべて（そのウィンドウ、タブ、フィールド、列、テーブル、メニュー項目、そしてバンドル自身のメニューノード）を、ログのひとつのグループとしてまとめて無効にします。古い Ninja と同じく、レコードを持つテーブルがあると実行が止められ、そのテーブルとレコード数が挙げられます。dry=Yは、何が無効になるかを答えます。システムに最初からあるテーブルは自分自身を保ち、バンドルが加えたものだけを失います（Business Partner のタブはなくなり、Business Partner は残ります）。二回実行すると、二回目は何も書き込みません。そのあとで同じワークブックにninja.execを実行すると、バンドルが戻ります。ninja.exportは、バンドル、ウィンドウ、またはテーブルを、ninja.execが読めるワークブックとして書き戻します。テーブル、Masterの結び付き、型付きの列、各一覧の値です。シートを編集して、もう一度実行できます。あるいはモデルをファイルとして別のマシンへ運べます。書き出すのはモデルだけで、行は決して書き出しません。すでにあるファイルは決して上書きされません。選択子（bundle=、window=、table=）がひとつ必要です。

    mis.list、mis.sum、mis.groupのmaster=Table/recordは、そのレコードの下にある行、つまりその下のタブが表示する行だけを残します。mis.list kind=PR_Visit master=PR_Patient/Aminahは、Aminah の診察です。スラッシュの後ろのレコードは、mis.update number=が読むのと同じように読まれる id、Document No、Name、または Value です。答えは、ふつうのフィルタPR_Patient_ID=1と同じです。マスターの下のタブではないテーブルは、理由とともに拒否されます。存在しないレコードや、ふたつのレコードが共有している名前も同様です（その場合は id を指定してください）。何も下にないレコードは、空の質問ではなく、本当のゼロです。

    答えの表示方法を選び、保存する¶

    返信は、特に指定しない限り JSON のエンベロープです。三つのスイッチで、答えの行を、人や表計算ソフトが読める形で表示できます。ドアが記録するのは、引き続きエンベロープです。

    • --list：桁をそろえた表。最後にshown N of TOTALが付きます。ひとつのレコードだけの返信は、field: valueの行で表示されます。
    • --csv：行を CSV で出力します（RFC 4180：コンマ、引用符、改行を含むセルは引用符で囲まれ、数値はエンジンが返したとおりです）。
    • --out FILEは、選んだ形式を、画面ではなくカレントフォルダのファイルに書きます。拒否、保留、または結論不能の行は、ファイルを書かず、そう告げます。
    $ node common/door/door.js --csv 'erp.list kind=Order docstatus=CO limit=3 columns=DocumentNo,DocStatus,GrandTotal sort=-DocumentNo'
DocumentNo,DocStatus,GrandTotal
80001,CO,100.7
80001,CO,100.7
800002,CO,2160

    スクリプトでは、行の末尾に> fileを付けると、その行の答えがスクリプトのフォルダのファイルに送られます（>> fileは追記）。形式は名前に従います。.csvは CSV、.jsonはエンベロープ、それ以外は一覧です。スクリプトのフォルダの外に出るパスは拒否されます。

    これらのスイッチは五つ目のファイルrender.jsにあります。ダウンロードで使う場合は、door.jsの隣に置いてください。

    curl -O https://red1oon.github.io/bim-ootb/common/door/render.js

    レガシー iDempiere のプラグインを作る（OSGi と 2Pack）¶

    本物の iDempiere サーバーに ERP のデータモデルを載せる人のためのものです。データモデルはワークブック（Excel）です。Application Dictionary のテーブルごとに一枚のシート（AD_Table、AD_Column、AD_Window、AD_Tab、AD_Field、AD_Menuなど）があり、レコードごとに一行、最初の行が AD の列名で、各行に名前を付けるKey列があります。ワークブックの別の行を指すセルはref:<Key>と書き、サーバーがすでに持っている行を指すセルはexisting:AD_Table:C_ProjectTaskと書きます。Pluginというシートが、プラグインの id、バージョン、説明を保持します。実例は BIM Document モデルで、bim-ootbリポジトリのerp/plugins/models/BIM_Document.xlsxです。

    ひとつのワークブックから二つのものが作られ、両者は分けて扱われます。

    作られるもの 保持するもの 置き場所
    2Pack の zip メタデータのみ：辞書の行と、プロセスのクラス名。プログラムのコードはありません。パックのバージョンは一度適用されたら変更されないので、同じバージョンで行が違うものは拒否されます プラグインのMETA-INFフォルダ。プラグインが起動するときに、iDempiere 自身のパックアクティベーターが拾います
    Java のモデルクラス ワークブックが作る各テーブルのI_<Table>とX_<Table>。iDempiere 自身のジェネレーターが書く形です プラグインのsrcフォルダ

    ワークブックが作れないのはルールです。テーブルの伝票アクションと、プロセスのコードです。これらは、どの iDempiere プラグインでもそうであるように、プラグインのsrcフォルダに手で書きます。

    ドアの動詞erp.pack book=<workbook.xlsx> version=<x.y.z> out=<plugin>/META-INFは、zip だけを書き、その sha256、辞書テーブルごとの行数、それが指すプロセスクラスの名前を答えます。同じバージョンと同じ行でもう一度実行するとunchangedと答えます。同じバージョンで編集されたワークブックは、リリース済みのパックは決して変更されないので、拒否されます。java=<plugin>/src package=<java package>を加えると、Java のモデルクラスも書かれます。人が実行します。AI の呼び出しは、人が承認するまで申請として保留されます。その下のスクリプトは、引き続きnode erp/tools/xlsx_pack.jsで、書き出すファイルごとに§XLSX-PACKの行を表示します。二つ目の動詞erp.legacy_plugin book=<workbook.xlsx> version=<x.y.z>は、ローカルのレガシーテスト環境での全行程を一行にしたものです。五つの行を実行し、ok でない最初の行で止まります。legacy.up（共有の docker Postgres が止まっていれば起動）、erp.pack（zip を作る）、legacy.refresh（基本のシードからテストデータベースを作り直し、プラグインをインストールし、サーバーを起動して、パックがインストールされるまで待つ。約二分）、legacy.check（ワークブックのすべての行を、テストデータベースから SQL で読み戻す）、legacy.witness（サーバー内のチェックをサーバーのコンソール経由で実行し、その判定と数を答える）です。各手順は単独でも実行できます。環境、そのデータベース、スクリプトは固定で、呼び出し側からは何も受け取らず、パイロットのデータベースは拒否されます。人が実行します。AI の呼び出しは、人が承認するまで申請として保留されます。

    legacy.checkは読み取り専用で、種類ごとに、いくつの行が見つかったかを、ワークブックが持つ数と並べて答えます。

    $ node common/door/door.js --list 'legacy.check book=erp/plugins/models/BIM_Document.xlsx'

    ふつうのダウンロードで Viewer に尋ねる¶

    二つの Viewer 動詞viewer.countsとviewer.clashesは、チェックアウトなしでも動きます。六つのファイルの隣に、さらに二つのファイルを置いてください。

curl -O https://red1oon.github.io/bim-ootb/viewer/tools/viewer_driver.js

    ディスクにページのファイルがないときは、ツールは、サイトが提供している建物とともにライブの Viewer ページを、プロセッサ上の非表示のブラウザで開き、Viewer 自身の Find パネルに尋ねます。答えのpageが、どのページが使われたかを告げます。

    $ node door.js 'viewer.counts building=Duplex' | grep -o '"summary":"[^"]*"\|"page":"[a-z]*"'

"page":"live"

    約三十秒かかります。数値は提供されている建物のもので、チェックアウトにある古いコピーとは違うことがあります。スケジュールの動詞、viewer.film_path、オブジェクトの動詞、modeller.walkは、まだチェックアウトが必要です。表にそれが書かれています。

    red1 シェル：ひとつのプロンプトで短い言葉¶

    red1は、キーボードの前にいる人のためのドアです。node common/door/red1.js（またはチェックアウトで一度npm linkした後はred1）と入力すると、red1>プロンプトが出ます。短い言葉はどれも、ドアのひとつの行になり、その行は実行される前に、→の後に表示されます。そのため、シェルは使いながら完全な行を教えてくれ、スクリプトや AI は、シェルなしで同じ行を実行できます。プロンプトに入力した完全なドアの行も、そのまま使えます。

    確認されないこと¶

    返信には、そのチェックが対象としなかったものが一覧されます。Modeller の編集レポートでは、一覧は次のとおりです。

    $ grep -o '"notChecked":\[[^]]*\]' widen.json | tail -1
"notChecked":["duplicate ids","elements changed outside the edit's own list","floating or unsupported elements","grid lines placed on top of each other","invalid coordinates","real beams: only girders walked from columns are span-checked","unknown element types","wrong units or absurd sizes, unless they hit something","zero-size elements","load capacity","beam and column rules (Regulatory Report only)"]

    同じ言葉は、どの答えにも当てはまります。重なりはまずバウンディングボックスで見ること、チェックは動いたものだけを対象とすること、そして耐荷重は決して確認されません。赤のない返信は、決して安全を意味しません。
