# DXF2BIM — Deterministic 2D DXF → 3D BIM

Status: SPEC v0.2 (2026-10-11), reviewed once, decisions §8 agreed by user. Code starts with S1-S3 + T1-T3 (see §10).

## 1. Goal
Same DXF in → same 3D BIM out, every run. Each 3D element records the DXF entity (handle, layer) it came from. Anything the DXF cannot supply is flagged as a gap, never filled by guess.

## 2. Why (sourced)
- Internal research: `2Dto3D/docs/RESEARCH_2D_TO_3D_APPROACHES.md` line ~663 "Market Gap": no open-source tool does automated 2D→3D. Revit/ArchiCAD are manual trace.
- Prior art, checked 2026-10-11 by fetching the pages (summaries from the fetch, not full source reads):
  - CrossBIM (github.com/AMostafaH/CrossBIM), SOURCE READ 2026-10-11 (clone, `HelperClasses/HelperFunctions.cs`, view models): student project, 2 commits, both 2021-12-12, no LICENSE file. ASP.NET Core 3.1 web form. Structural only: columns, beams, slabs (+openings, drop panels), isolated footings, strip footings. No walls, doors or windows in the code. User types, per category, the DXF layer name plus depth/width/thickness/top level into a form; height per storey and repeat count replicate one DXF floor upward. Output via Xbim to IFC4 (+ifcxml, wexBIM preview uploaded to Cloudinary). The DXF reading and IFC geometry code (`CrossBIMLib`: DXFBeam/DXFColumn/DXFSlab, IFCBeam etc.) is a prebuilt `CrossBIMLib.dll` with no source in the repo, so its internals are unreadable. Deterministic in the sense that user-supplied layer→dimension tables drive output; no provenance, no gap reporting, no undo. Same idea as our R1/R3, narrower scope (structure only).
  - IfcOpenShell issue #1950 (open; reopened 2026-07-26): the script there (ezdxf + ifcopenshell) maps LINE/ARC/CIRCLE/POLYLINE/SPLINE/ELLIPSE to IFC curves only. No walls, no extrusion, no heights. Also `src/blenderbim/dxf2ifc.py` (v0.7.0), handles solids; current existence not confirmed.
  - co2tools (github.com/Mambix/co2tools): DXF→STL extrude per part, YAML config (`extrude`, `translate`, `rotate`). Manufacturing panels, not buildings, no IFC. Config-driven extrusion is the same pattern as our R3.
  - IFCraft: not fetched; Gemini's description (civil/alignments focus) unverified.
- Claim to use: "no general, deterministic FOSS DXF→BIM tool found" (not "none exists"). CrossBIM source read: it supports the claim (structural only, closed DLL, no walls/doors/windows).

## 5. Determinism rules (draft)
- R1 Fixed layer→element-type map (table in DB, versioned), no inference outside it.
- R2 Fixed processing order (sort by handle).
- R3 Missing height/thickness/material → explicit gap record; value only from a config the user supplied.
- R4 Provenance column on every element: DXF handle + layer.
- R5 Round-trip: DXF → 3D → DXF (existing writer) must match input geometry within stated tolerance.

## 6. Pipeline stages

Runs in the Modeller (`deploy/dev/`). Each stage is a pure function of its input plus the two user-supplied tables (layer map, config). Each stage writes a log line per decision (kept/skipped/gap + reason). Read the log after every run.

Inputs (all user-supplied, versioned, hashed into the run record):
- `dxf` — the file, read as bytes
- `layer_map` — layer name pattern → element type (R1). Starts from AIA/NCS guides in `2D_Layout/reference_samples/` and the `2d_dxf_layer` table.
- `config` — storey heights, wall thickness/height per type, units (R3). Same role as `2Dto3D/building_config.json`.

| # | Stage | Input → Output | Deterministic because | Gap case |
|---|---|---|---|---|
| S0 | Hash | file bytes → `run_id` = hash(dxf, layer_map, config) | no clock/random in id | — |
| S1 | Parse | DXF → entity list `{handle, type, layer, geometry}` via `dxf-parser.js` | sorted by handle (R2) | unsupported entity type → `GAP:unsupported_entity` |
| S2 | Units/origin | `$INSUNITS` + config → metres; origin = config value, else DXF 0,0 | explicit rule, no bbox guessing | `$INSUNITS` missing and no config units → stop, ask |
| S3 | Classify | entity.layer → element type via `layer_map` | table lookup only (R1) | layer not in map → `GAP:unmapped_layer`, entity skipped |
| S4 | Topology | classified 2D → candidates: LINE/LWPOLYLINE on wall layers → wall centreline segments; closed polylines → slab/room outlines; INSERT → component placement (block name, point, rotation, scale); ARC → curved segment | snap tolerance is a config number; endpoints joined in handle order | open outline where a closed one is required → `GAP:unclosed` |
| S5 | Extrude | candidates + config → 3D parameters (wall: path, thickness, height; slab: outline, thickness, level; component: block ref + transform) | heights/thicknesses read from config only (R3) | no config value for the type → `GAP:no_dimension`, no element |
| S6 | Emit | 3D parameters → kernel ops via `commitOp` (`kernel_ops.js`); element GUID = hash(run_id, handle) | same input → same GUID; provenance (R4) in `parameters` | — |
| S7 | Report | counts per stage, all GAP records, run_id | — | — |

Notes:
- New `op_type` values: see §8.4 (`DXF_RUN`, `DXF_WALL`, `DXF_SLAB`, `DXF_COMPONENT`, `DXF_OPENING`, `DXF_GAP`). `commitOp` doc lists only GRID_MOVE | VIEW_FILTER | GRID_DETECT today.
- Annotation layers (A-DIMS, A-NOTE, TEXT, MTEXT, DIMENSION, Defpoints) are mapped to `ignore` in `layer_map`, not hardcoded. Logged as skipped.
- Dimension/text use: may later feed config suggestions. Out of scope for v1; suggestions never auto-applied.
- INSERT to component: block name must resolve in the component library. Unresolved → `GAP:unknown_block`.
- Walls: `wall_mode = centreline` only in v1 (§8.5).

Sample reality check (`jscad_floorplan.dxf`, counted from the file): 1,989 LINE, 402 LWPOLYLINE, 285 INSERT, 126 DIMENSION, 80 ARC. Layers include xref-prefixed ones (`xref-Bishop-Overland-08$0$A-WALL`, `…A-OPENING`, `…R-TRUSS`, `…S-FOOTER`). So it is not a small clean file. `layer_map` must match on pattern, e.g. suffix after the last `$`. Openings: see §9.

## 7. Layer map format and tests

### 7.1 layer_map (R1)
JSON, versioned, hashed into `run_id`. Ordered list, first match wins (order is part of the hash).
```
{ "version": 1,
  "rules": [
    { "match": "suffix", "pattern": "A-WALL",    "type": "wall" },
    { "match": "suffix", "pattern": "S-SLAB",    "type": "slab" },
    { "match": "suffix", "pattern": "A-DOOR",    "type": "component" },
    { "match": "suffix", "pattern": "A-OPENING", "type": "opening" },
    { "match": "exact",  "pattern": "A-DIMS-1",  "type": "ignore" }
  ] }
```
- `match`: `exact` | `suffix` (text after the last `$`, so `xref-X$0$A-WALL` matches `A-WALL`) | `prefix`. No regex in v1.
- `type`: `wall` | `slab` | `component` | `opening` | `ignore`. Anything else is rejected at load.
- No rule matches → `GAP:unmapped_layer`.
- Seed rules come from the AIA/NCS PDFs in `2D_Layout/reference_samples/` and the `2d_dxf_layer` table. Seeding is a copy step by a human, not inference.

### 7.2 config (R3)
```
{ "version": 1, "units": "m", "snap_tol": 0.001, "wall_mode": "centreline",
  "wall": { "thickness": 0.2, "height": 3.0, "base": 0.0 },
  "slab": { "thickness": 0.2, "level": 0.0 } }
```
Missing key → GAP at S5, never a default. (`wall.base` added at coding: a wall without a base level cannot be placed.)

## 8. Decisions (AGREED by user 2026-10-11)
1. Modeller file: CLOSED, §3.
2. Extractor: **port to JS, do not reuse the Python.** Evidence: `2Dto3D/Scripts/generate_3d_geometry.py` hardcodes `DEFAULT_WALL_THICKNESS=0.2`, `DEFAULT_WALL_HEIGHT=3.0`, door 0.9x2.1, window 1.2x1.5. That breaks R3 (no invented values). The Python stays as reference only. Reader: `dxf-parser.js` already in `deploy/dev/`.
3. Test DXFs: CLOSED. F1 (§7.3) for T1-T7, `jscad_floorplan.dxf` for T8 (report only).
4. op_type names: follow the existing `NOUN_VERB` upper-case style (`GRID_ADD`, `GRID_MOVE`, `DISC_SWITCH`): `DXF_RUN` (one per import, holds run_id, hashes, counts), `DXF_WALL`, `DXF_SLAB`, `DXF_COMPONENT`, `DXF_OPENING`, `DXF_GAP`. Undo of a run = undo all ops with that run_id.
5. Walls v1: `wall_mode = centreline` only. Double-line (pair) walls are v2; a drawing that uses pairs gets `GAP:wall_pair_unsupported` rather than a guess.
6. Openings v1: add layer_map type `opening`. Each opening entity is emitted as `DXF_OPENING` (position, width from the entity). **No cut into the wall in v1**; each gets `GAP:no_host_cut`. Cutting needs a rule for which wall hosts the opening and a sill/head height from config; that is its own spec section (§9, not yet written).
   -> Detailed in §9.
7. Double-encoding: CONFIRMED by code reading 2026-10-11 (not run against a live DB). `commitOp` does `JSON.stringify(params)` itself (`kernel_ops.js` ~l.53). 9 call sites pass an already-stringified value: `doc_canvas.js` (GRID_ADD x2, GRID_CALIBRATE, DISC_SWITCH, GRID_DELETE x2, GRID_MOVE x2) and `route_walker.js` (ELEMENT_PLACE). Those rows store a JSON string inside JSON. `replayOps`/`undoOp` parse once and return a string, so `op.parameters.axis` etc. are `undefined` for them. Worst case in `compact` (`kernel_ops.js` ~l.168): for such GRID_MOVE rows `pCurr.label === pNext.label` is `undefined === undefined`, so consecutive ones may be collapsed regardless of label. Call sites passing objects are fine (`grid_drag.js`, `grid_overlay.js`, `grid_dims.js`, `grid_recompose.js`, `picking.js`, `section_cut.js`). Also `route_walker.js` passes `inputGuids` as a bare string, but the doc says Array.
   - Rule for DXF2BIM: always pass an object to `commitOp`, never a string; `inputGuids` an array.
   - T7 adds: `typeof JSON.parse(parameters) === 'object'` for every DXF op.
   - Existing bug handled in `KERNEL_OPS_ENCODING_SPEC.md` (partly fixed in `deploy/dev/kernel_ops.js`, uncommitted). 9 call sites, not 10.

## 9. Openings (doors/windows)

Status: SPEC 2026-10-11. Extends §6 S4/S5 and decision §8.6.

### 9.1 Evidence (counted from `jscad_floorplan.dxf`, layer containing "OPENING")
`xref-Bishop-Overland-08$0$A-OPENING`: 145 LINE, 11 ARC, 3 LWPOLYLINE, **0 INSERT**. So in this real drawing openings are raw geometry (jamb/sill lines and door-swing arcs), not named blocks. Other layers hold INSERTs, but those are fixtures (FIXT-*, P-Toilet), not openings. Other drawings may use blocks; v1 must handle both without guessing.

### 9.2 Opening sources (v1)
| Source on an `opening` layer | Rule | Result |
|---|---|---|
| INSERT whose block name is in the component library | position, rotation from entity; width/height from library entry | `DXF_OPENING` |
| ARC | door-swing: hinge = arc centre; leaf width = arc radius (value from the DXF, not a default); swing sector = start/end angle | `DXF_OPENING` kind `door` |
| LINE / LWPOLYLINE | no deterministic rule in v1 | `GAP:opening_unclassified` (one per entity) |
| INSERT not in library | — | `GAP:unknown_block` |
Window detection from line pairs is OPEN (needs its own evidence: how sample drawings draw windows).

### 9.3 Host wall rule
For each `DXF_OPENING` with a point P (hinge or insert point):
1. Candidates = wall centreline segments (S4) with point-to-segment distance ≤ `host_tol` (config, no default).
2. Pick smallest distance; tie → lowest DXF handle (numeric).
3. No candidate → `GAP:no_host`.
Result stored as `host_wall` = that wall's element GUID. Depends only on geometry and handles, so order-independent (R2).

### 9.4 Dimensions
Width: from the entity (ARC radius or library entry). Door head height, window sill/head: config keys `opening.door.height`, `opening.window.sill`, `opening.window.height`; missing → `GAP:no_dimension`. Never defaulted (contrast `generate_3d_geometry.py` DEFAULT_DOOR_*).

### 9.5 Cut
v1: no boolean cut; each opening carries `host_wall`, hinge/centre, width, and `GAP:no_host_cut`. Cut is enabled (v1.1) only after tests O1–O5 pass, as a separate op `DXF_WALL_CUT` referencing the opening, so it is undoable on its own.

### 9.6 Fixture F2 `f2_openings.dxf` (F1 plus)
- `A-OPENING`: ARC centre (2.0, 0.0), radius 0.9, angles 0°–90°
- `A-OPENING`: ARC centre (50.0, 50.0), radius 0.9 (far from every wall)
- `A-OPENING`: 3 LINEs near (4.0, 4.0)
- `A-OPENING`: ARC centre (0.0, 0.0), radius 0.8 (corner: equidistant to two walls)
Config adds `host_tol` = 0.3, `opening.door.height` = 2.1.

## 10. Review notes and added rules (2026-10-11)
Gaps found on review, now rules:
- N1 Hash: SHA-256 hex over canonical JSON (keys sorted, no whitespace) of {dxf hash, layer_map, config, sorted component-library block names} (the library is an input). `crypto.subtle` is async in browsers; Node tests use `crypto`. The module takes a hash function as an injected dependency.
- N2 Sort by handle = numeric value of the hex handle, not string order.
- N3 Scope v1: modelspace `ENTITIES` section only. BLOCK definitions and xref contents are not expanded; an INSERT is one placement. Anything inside blocks is not read (logged once as `SKIP:block_content` count).
- N4 Element GUID = hash(run_id, handle, part_index). Needed because one entity can yield several elements (a polyline wall gives one per segment).
- N5 Numbers: coordinates rounded to 6 decimals before comparison, hashing and emit, so float noise cannot change output.
- N6 Wall corners: v1 emits one box per segment about the centreline; boxes overlap at corners. No mitre/join. Quantities at corners are therefore approximate; stated, not hidden.
- N7 T6 feasibility OPEN: the existing writer (`drawing_writer_dxf.py` / Java `DxfWriter`) reads `output.db`, not kernel ops. A round trip needs either an op-to-DXF step or the browser `deploy/dev/dxf_export.js` (308 lines, unread). T6 stays unwritten until this is checked.
- N8 Slab level and wall base level both come from config; no storey inference in v1.


## 10b. Added after sandbox probe (2026-10-11)
- N9 Units: `jscad_floorplan.dxf` has `$INSUNITS=4` (millimetres) and 948 modelspace entities (earlier "1,989 LINE" etc. counted BLOCK definitions too; §6 sample note is therefore wrong for modelspace). v1 must convert, not stop. Table (DXF $INSUNITS): 1 inch 0.0254, 2 foot 0.3048, 4 mm 0.001, 5 cm 0.01, 6 m 1. `config.units` (one of `in|ft|mm|cm|m`) overrides the header; unknown code and no config → stop. All DXF coordinates are multiplied by the factor and then rounded (N5); all config dimensions are in metres. Output is always metres. Test U1: F1 drawn in mm equals F1 in m (params).
- N10 Sandbox config values (thickness, height, base, level) for a messy file are placeholders chosen to exercise the pipeline, labelled `SANDBOX` in the log. They are not read from the drawing.

## 13. Mesh and assembly (spec, 2026-10-11)
Goal: from the ops of one or more storey DXFs, produce a deterministic triangle mesh and one assembled model. Module `deploy/dev/dxf2mesh.js`, pure, no DOM, no Modeller wiring. Defaults taken from the earlier recommendation (A-WALL hosts only, host_tol 0.15 m, snap_tol 0.0127 m); the user can change them in the config.
Decisions made here (tell me to change):
- M-a Z convention: storey `level` L (metres, from the manifest). Wall: z from `L + wall.base` to `L + wall.base + wall.height`. Slab: TOP surface at `L + slab.level`, bottom `thickness` below. Door opening: z from `L` (floor level) to `L + door.height`. Rect opening: z from `L + rect.sill` to `+ rect.height`.
- M-b Wall = box about the centreline: width along the wall = segment length, thickness `wall.thickness`, normal = left of the start→end direction. Corners overlap (N6); volumes are summed, not unioned.
- M-c Openings cut walls by SPLITTING the wall box into boxes (no boolean): full-height pieces between openings, a lintel above, a sill piece below. Door span on the wall axis = from the hinge to whichever of the two arc end points lies nearer the host wall axis (tie → start angle). Rect span = projection of the centre on the axis, half-extent `width/2*|cos d| + depth/2*|sin d|` (d = angle between rect long axis and wall). Opening thickness = host wall thickness. Openings are voids only; no door leaf or window glass mesh in v1 (stated gap `GAP:no_fill_geometry`).
- M-d Clipping is never silent: an opening that leaves the wall segment (axis range or z range) or overlaps an earlier opening on the same wall is NOT cut and gets `GAP:opening_outside_wall` / `GAP:opening_overlap`; the wall stays whole there.
- M-e Components (INSERT) have no geometry source (the library carries names only): `GAP:no_geometry`, not meshed.
- M-f Triangulation: boxes = 12 triangles in fixed order; slab = ear clipping (smallest vertex index first), ring forced counter-clockwise; simple polygons only (self-crossing → `GAP:bad_outline`).
- M-g Output: `{guid, class, handle, layer, vertices:[[x,y,z]...], faces:[[i,j,k]...]}` per element, coordinates rounded 6 dp (N5), plus `toObj()` text. Element classes: `IfcWall`, `IfcSlab`. Guid of a wall piece = hash(wall guid, piece index).
- M-h Assembly: manifest `{name, storeys:[{name, level, file}]}`; each storey is run through `dxf2bim.run` with the same layer_map/config/library and meshed with its level. All storeys share one coordinate origin (assumed, then checked): per-storey extents are logged and `WARN:storey_extent_mismatch` is raised when the extent centres differ by more than `config.align_tol` (required for assembly; missing → stop). Assembled `run_id` = hash(canonical manifest + storey run_ids in manifest order). 2D elevation/section sets are NOT used for heights in v1 (heights come from config).

## 24. Markings: view, face, axis, anchors, levels (spec, 2026-10-11)
Rule agreed by user: every DXF in a set carries its own markings; the pipeline never infers view type, orientation, or datum. Markings may be added to a drawing before processing (by a person, or by a tool/model after looking at the drawing); the reader only reads.
Format: TEXT entities on layer `DXF2BIM-MARK`, one marking per entity, text `@KEY=VALUE` (no spaces around `=`). The entity's insertion point carries position where a key needs one. Keys:
| Key | Where | Value | Position used |
|---|---|---|---|
| `@SET` | all | set name (all drawings of one building share it) | none |
| `@VIEW` | all | `PLAN` or `ELEV` | none |
| `@NAME` | all | free label (e.g. `FRONT`) | none; informational only, never decides axes |
| `@UNITS` | all | `mm|cm|m|in|ft` | none; overrides `$INSUNITS` |
| `@LEVEL` | PLAN | storey level in metres | none |
| `@GRIDX` | PLAN | grid label of a line at constant x | x |
| `@GRIDY` | PLAN | grid label of a line at constant y | y |
| `@FACE` | ELEV | `minX|maxX|minY|maxY` = which building face is shown (plan axes) | none |
| `@HAXIS` | ELEV | `+X|-X|+Y|-Y` = which plan axis the drawing's +x (horizontal) runs along | none |
| `@GRIDH` | ELEV | grid label of a line seen in this elevation | x (horizontal) |
| `@Z` | ELEV | height in metres of a true level line | y (vertical) |
Validation (errors, never defaults): unknown key; malformed value; duplicate key with a different value (`@GRIDX=A` twice at different x is a conflict); PLAN requires `@SET @VIEW @LEVEL @UNITS` and at least 2 `@GRIDX` and 2 `@GRIDY`; ELEV requires `@SET @VIEW @FACE @HAXIS @UNITS`, at least 2 `@GRIDH`, at least 2 `@Z`; `@HAXIS` must be perpendicular to the face normal (minY/maxY faces take ±X, minX/maxX take ±Y) so a mirrored declaration is allowed but a nonsensical one is not; a missing required key stops processing of that drawing with `MARK:missing <keys>`.
Alignment check (deterministic, reader side): plan grid positions give coordinates per label. For an elevation, with `HAXIS = s*axis` (s = +1 or -1), the plan coordinate of horizontal position h is `c(h) = c_L + s*(h - h_L)*k` for any shared label L (k = units to metres). Every shared label must agree within `align_tol`; fewer than 2 shared labels, or any disagreement, → `MARK:align_fail` with residuals. Vertical: `@Z` pairs must satisfy `(z_j - z_i) = (y_j - y_i)*k` within `align_tol`, else `MARK:level_scale_fail`. Height of a drawn feature at y: `z = z_i + (y - y_i)*k`.
Evidence for why `@HAXIS` is explicit: the old BIM→2D writer's LEFT elevation (face minX) runs drawing-x along +y and its RIGHT (maxX) along -y; FRONT (minY) +x and REAR (maxY) -x (checked on window tags and grid labels in `DX_*_20260428_0636.dxf`). Face names would mislead.
Tests (hand-computed fixtures): MK1 read every key from a fixture and return the structured descriptor · MK2 unknown key, malformed value, conflicting duplicate each rejected with a named error · MK3 missing required keys → `MARK:missing` listing exactly them · MK4 HAXIS vs FACE perpendicularity (minY with +Y rejected; minX with -Y accepted) · MK5 alignment passes for a mirrored REAR (s=-1) with shared labels A,B at known positions and fails when one grid is moved 100 mm · MK6 `@Z` scale check: wrong scale fails · MK7 write then read round trip (writeMarks inserts into the ENTITIES section; dxf-parser reads them back) and the original entities are untouched · MK8 the DXF still parses and renders order-independently (marker order in the file does not change the descriptor).
Then (§25) the Duplex set is marked by a sandbox tool from evidence in the files (titles, grid labels, level lines), reviewed against rendered images, and verified: alignment residual must be 0 against the known plan, and window tags must land where the markings say.

## 42. Preferred set in type binding (spec, 2026-10-12)
User agreed (2026-10-12) to the recommendation of §41: a preferred-family setting, explicit bindings as override. Generalised to SETS: a set is a named group of library entries (a product family, a BOM, a supplier range). A set is the unit a user picks; "prefer" is the rule that lets a set break a size tie.
- S1 A library entry may carry `set` (string). Entries without `set` are never preferred.
- S2 `cfg.bind.prefer` = ordered list of set names (optional; absent = no preference, behaviour as §38). Used ONLY in the size step with more than one candidate: take the first set in the list that has at least one candidate; if exactly one candidate in that set → bind, `bind_source: "size_prefer"`, `type.preferred_over` = the other candidate ids (sorted), `type.set`. If that set still has several candidates → `GAP:type_unbound` as before with `candidates` (all) and `prefer_narrowed` (the set's). If no listed set has a candidate → as before.
- S3 `prefer` never overrides an explicit binding or a label hit, never rescues a size mismatch (candidates are chosen by size first), and does not apply when there is exactly one candidate (that bind stays `size`, even if its set is not preferred).

## 44. Labels and schedules by marking (spec, 2026-10-12)
Why: the geometry cannot tell two products of the same size apart (§43: 12 Duplex windows 819x759, Fixed vs Casement; Farmhouse window mark 1: schedule 60 in vs elevation 78 in). The information is in the drawing's text (a legend, a schedule, a tag next to the element) or in the user's head; the marking step states it. Same principle as `@OPENING`: the marker author looks at the drawing and states, the pipeline reads and does not guess.
- L1 `@LABEL=class,x,y,text` (PLAN view only; repeatable): `class` = `door|window|wall`; `x,y` = a point in drawing units on or in the element; `text` = the label (everything after the third comma; non-empty). A label text equal to a library id binds through §38 B3 step 2 (label); any other text is a schedule mark.
- L2 `@SCHEDULE=text,class,w,h` (door|window) or `@SCHEDULE=text,wall,t` (repeatable, any view; drawing units, converted with `@UNITS`): the size the drawing's schedule states for that mark. Used only for the conflict check (B5); never to overwrite measured values and never to bind by itself.
- L3 `describe` returns `desc.labels` (`{class,x,y,text}`) and `desc.schedule` (`{text,class,w,h|t}`), canonical order, exact duplicates merged. Errors: bad class/arity/number → `MARK:malformed`; same (class,x,y) with two texts, or same schedule text+class with two sizes → `MARK:conflict`.
- L4 `applyLabels(ops, desc)` (in `dxf2types.js`, pure): the point (drawing units × `UNITS[desc.units]`) selects the op(s) of that class whose plan footprint contains it (±`snap_tol` passed in options): wall → `rect`; window → `bbox` if present else centre ± width/2 along the axis and ± depth/2 across; door → within `width` of `hinge` (the swing disc; SANDBOX rule, stated). Exactly one op → `params.label = text`, `params.label_source = "marking"`. Zero → `GAP:label_unmatched`; more than one → `GAP:label_ambiguous`, nobody labelled; an op that already has a different label → `GAP:label_conflict`.
- L5 `scheduleFromDesc(desc)` → `{text: {class, width, height | thickness}}` in metres for `bindTypes opts.schedule`; `bindTypes` ignores a schedule entry whose class differs from the element's.
Tests: LB1 parse, canonical order, bad arity/class/number rejected, per-view leak · LB2 label lands on exactly the window it points into · LB3 point in no element → `label_unmatched` · LB4 point in two overlapping elements → `label_ambiguous`, none labelled · LB5 door by hinge disc · LB6 unit independence: the same point in mm and in inches labels the same element · LB7 library-id label end-to-end: two same-size library products in one set are told apart by the label (the Duplex 819x759 case) · LB8 schedule conflict end-to-end with inches (60 in vs 78 in) reported with both values in metres · LB9 existing different label → `label_conflict` · LB10 order independence of markers · LB11 schedule entry of another class ignored by `bindTypes`.
Duplex use (round trip, labelled as such): the marking step for the exported Duplex set takes the window type from the SOURCE model (`M_Fixed` / `M_Casement`) and writes `@LABEL=window,x,y,DUPLEX_SMALL_FIXED|DUPLEX_CASEMENT`. This proves the mechanism, not discovery: on a real drawing the label comes from its legend or from the user.
- L1b (added after the Duplex run, 2026-10-12): STACKED openings share one plan footprint (Duplex Level 2: three 819x759 windows per plan position, sills 0.1 / 0.9255 / 1.751 m above the level, source z 3.2 / 4.0255 / 4.851 m). A plan point alone is then `GAP:label_ambiguous` (correct behaviour, seen in the first Duplex run: 0 of 12 labelled). Fix: an optional 4th field `z=<metres>` (absolute z, same convention as `@Z`): `@LABEL=window,x,y,z=4.1,TEXT`. With `z`, only elements whose absolute z interval contains `z` can match: opening → `[level+sill, level+sill+height]`, wall → `[level+base, level+base+height]`; an element without those numbers never matches a `z` label. `applyLabels` takes `opts.level` (metres, required when any label has `z`, else `GAP:no_dimension`). `desc.labels[i].z` present only when given; `z` is part of the duplicate/conflict key. Tests: LB13 `z` picks one of three stacked windows · LB14 `z` outside every interval → `label_unmatched` · LB15 parse of `z=`, malformed `z=abc`, same point different `z` are different labels.

## 52. Tags: canned labels placed on the drawing (spec, 2026-10-12)
User direction: canned labels and markers placed by users on their drawings help a lot; build the label reader. Until now `@LABEL` needed typed coordinates. A TAG is the same information placed by position: the user puts a text on the drawing at the element (plan) or at the opening (elevation); the reader takes the position from the text's insertion point.
- T1 `@TAG=class,text` (marker text on the marker layer; `class` = `door|window|wall`; repeatable; PLAN or ELEV view). PLAN only: `@TAG=class,z=<metres>,text` (same `z=` as §44 L1b). Position = the marker's insertion point `(x, y)` in drawing units. `describe` returns `desc.tags` = `{class, x, y, [z], text}` canonical order; exact duplicates merged; same class+position (+z) with two texts → `MARK:conflict`; `z=` in an ELEV view → `MARK:malformed` (z comes from the position); bad class, empty text → `MARK:malformed`.
- T2 Canned vocabulary (optional): `opts.vocab` = object `{tagText: labelText}`. With a vocabulary the tag text must be a key (case-sensitive) and the label becomes the mapped value (short canned codes → library ids); a text not in the vocabulary → `GAP:label_unknown_text` (typo protection), nothing labelled. Without a vocabulary the tag text is used as the label as is.
- T3 PLAN tag → label via the §44 matching (point inside the element's footprint, class, optional z; same gaps `label_unmatched/ambiguous/conflict`).
- T4 ELEV tag: the position `(h, y)` is mapped through the plan↔elevation alignment (`map.toPlan(h)` along the face axis, `map.zOf(y)` height). It labels the opening ops of the tagged class whose `face` equals the view's `face`, whose plan interval along the face axis contains the mapped coordinate (±`snap_tol`), and whose absolute z interval `[level+sill, level+sill+height]` contains the mapped z. Stacked openings are therefore told apart by the tag's height without typing `z=`. Zero → `GAP:label_unmatched`; several → `GAP:label_ambiguous`; walls cannot be tagged in ELEV (→ `GAP:label_unmatched`).
- T5 API: `applyTags(ops, views, units, opts)` in `dxf2types.js`; `views` = `[{desc, map?}]` (described views; `map` from `Dxf2Marks.align` for ELEV views); `opts` = `{snap_tol, level, vocab}`; returns `{ops, gaps, labelled}` like `applyLabels`.
Tests: TG1 parse (valid, canonical, duplicates merged, malformed, conflict, `z=` rejected in ELEV) · TG2 plan tag at its insertion point labels the element under it · TG3 plan tag with `z=` picks one stacked opening · TG4 vocabulary alias resolves to the library id · TG5 text not in the vocabulary → gap, nothing labelled (case-sensitive) · TG6 elevation tag picks the right one of three stacked windows by height · TG7 elevation tag of another face does not label · TG8 elevation tag at a height with no opening → unmatched · TG9 end to end: two same-size products told apart by tags, then bound · TG10 order independence · TG11 a plan tag and an `@LABEL` on the same element with different texts → `label_conflict`.
