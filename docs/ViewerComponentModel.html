Call path, load to bar

building .db→ schedule_author→ schedule_gate→ cpm_schedule→ time_machine→ Gantt bar
  • schedule_gate computes a start time per element from geometry — support below, host wall, carrier above — plus crew capacity.
  • cpm_schedule rebuilds those relations as a graph and runs a forward pass. Physics edges and convention edges (trade order, storey order) go into the same graph, which is where the cycle comes from.
  • time_machine groups the finished element times by storey | phase into Gantt bars. Each bar's span is the earliest start to the latest end of its members — a hull, not a scheduled activity.

ConsequenceScheduling happens per element; display and measurement happen per group

Hospital schedules 63,182 elements individually, then draws them as roughly 54 bars. One outlier element stretches its whole bar — the effect the code itself calls "one pile, full project length." The same hulls are what the acceptance metric measures, so a stray element registers as a phase-ordering failure. Three symptoms, one cause: the unit of scheduling is not the unit anyone looks at.

What an IDE would and would not tell you

  • It would show the strata above, the fan-in table, and dead exports like schedule_engine.js — all of it derivable from source, which is how this page was built.
  • It would not show the runtime dependency graph, which is where every open defect in 4D lives. That graph is constructed from bounding-box geometry at load time and exists only in memory: 2.46 million edges on Hospital, none of them written to any file.
  • The gap matters because the fix is to persist those relations into task_sequences — an IFC-native table that already exists and holds zero rows on every shipped building. Once dependencies are data, they become reviewable, editable, and diffable. Until then no tool, IDE or otherwise, can inspect them.
