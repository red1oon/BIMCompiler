    Replication Flow Rows — a guide with ready-made patterns¶

    Generated by build/scriptor/gen_patterns_doc.js from build/scriptor/patterns.json and the compiler itself; checked by scripts/witness_scriptor_patterns.js. Every row below is a sample: copy it, change what the pattern says to change, compile it.

    1. What a flow row is¶

    A flow row is one line of data that says: this kind of record moves, in this direction, between these people, and this is the key that makes one record unique. You do not write code for it. The compiler reads the row, reads the dictionary (the Application Dictionary: tables, columns, references, windows), and works out the rest: which other tables the receiver must already hold, which columns the system computes by itself, and what is missing.

    Three parts work together, and you only touch the first:

    Part What it is Who touches it
    The row the declaration, the pages below you
    The treatment the component that knows how to carry out one kind of row (FACT, SEED, RULE, INSTRUMENT, LOCAL). The row names it; it is found by name in a registry, like a factory. an engineer, only to add a new kind
    The plan reader what the Modeller or the ERP uses to ask "is this table shared?" the application author

    2. The fields of a row¶

    Field Plain meaning Example
    name A label you choose. Other rows refer to it by this exact text. F1 pos-sales-up
    treatment The kind of movement. FACT = a record moves. SEED = a value is published and fetched. RULE = a named process that sends another flow, started by a flow arriving or by a role on a schedule. INSTRUMENT = a signed code that carries value. LOCAL = this table never leaves its station. FACT
    role The dictionary role (a number) of the devices that send. A label such as BORROWER is fine where there is no dictionary role. On a RULE with no on: the role that runs the process. 103
    strategy Which dictionary replication strategy supplies the table types. 100 is the sample point-of-sale strategy. 100
    dir UP = device to head office. DOWN = head office to a device. BOTH = every member of a team, both ways (needs audience space). UP
    audience For a FACT: hub (the default, through head office) or space (a team shares it). For a SEED: addressed (one role) or public (anyone). space
    table The dictionary table whose records move, or a table you declare yourself (section 4, pattern P7). C_OrderLine
    carries The columns that travel. Leave it out and the dictionary proposes columns (a starting point, never a plan). "*" means all of them. ["M_Product_ID", "QtyEntered"]
    group What makes one record unique, so that a resend is recognised and a clash is noticed. POSStation/Date/Order#
    schedule A label for when the device sends (or, on a RULE with a role, when that role runs the process). It is recorded in the plan. end-of-day
    from, to Free text for people reading the plan. POS station, HQ
    on, process, emits For a RULE: the named process sends flow emits. Either flow on arriving starts it, or a role on a schedule does (give role and schedule and leave on out; a person or department runs it, as in the dictionary). on and emits must be names of other rows in the same file. Replenish Report
    processId For a RULE: the dictionary process number the process name stands for (a whole number, for people reading the plan). 53267
    guard For a SEED: daily = ask at most once a day; once = ask only until you hold a value. daily
    authorityRole, holderRole, account For an INSTRUMENT: who issues the code, who applies it, and what the balance is called. 103, PHONE, loyalty id
    virtualTable, columns A table you describe yourself because the dictionary does not know it. Each column has name, cls, and optionally target, mand, values. see P7
    cls What kind of column: KEY (identity), REF (points to another table, needs target), MEASURE (a number), DATE, FLAG (yes or no), CODE (a short code, may have values), TEXT, OTHER. MEASURE
    target For a REF column: the table it points to. AD_User
    mand The column must be present when the record is created. true
    values For a CODE column: the list of allowed kinds. Adding a kind later is adding one value, not code. ["GEOM_EXTRUDE", "GEOM_SWEEP"]

    5. Write your own in six steps¶

    1. Say in one sentence what should move, who sends it and who receives it.
    2. Find your sentence in the table in section 3 and open that pattern.
    3. Copy its rows into a new file (a list of rows) and change only what "Change these" says.
    4. Compile it: node build/scriptor/compile.js yourfile.json.
    5. Read the report. A line starting x is a mistake and must be fixed. A line starting ! is a question to answer, not always an error. A line starting i is a fact (for example, what the receiver must already hold).
    6. Keep your file: the rows are the source, the plan is generated from them. Never edit a generated plan by hand.

    The count after "carries" includes three identity columns (the record id, the client and the organisation) that always travel.

    6. Common mistakes — and exactly what you will see¶

    M1 — A column name with a typo¶

    Start from pattern P1. In the row "F1 pos-sales-up": set carries to ["M_Product_ID","Qty_Entered","C_UOM_ID"].

       x unknown column(s): Qty_Entered

    Fix: Use the exact dictionary column name (QtyEntered).

    M2 — A table that does not exist¶

    Start from pattern P1. In the row "F1 pos-sales-up": set table to "C_OrderLine_X".

       x no such table: C_OrderLine_X

    Fix: Check the table name in the dictionary.

    M3 — A required setting left out¶

    Start from pattern P1. In the row "F1 pos-sales-up": remove group.

       x FACT needs group

    Fix: Say what makes one record unique (the group).

    M4 — Both ways, but not as a team¶

    Start from pattern P6. In the row "T1 bpartner-shared": set audience to "hub".

       x FACT dir BOTH needs audience space (a star has no both-ways)

    Fix: Both-ways flows are for a team: set audience to space.

    M5 — A team flow that only goes one way¶

    Start from pattern P6. In the row "T1 bpartner-shared": set dir to "UP".

       x FACT audience space needs dir BOTH

    Fix: A team shares both ways: set dir to BOTH.

    M6 — A kind of movement that is not registered¶

    Start from pattern P1. In the row "F1 pos-sales-up": set treatment to "FACTS".

       x unknown treatment FACTS

    Fix: Use FACT, SEED, RULE, INSTRUMENT or LOCAL, or register a new treatment.

    M7 — A made-up kind of column¶

    Start from pattern P7. In the declaration of bim_element: change the column pos_x so that cls is MONEY.

    x V1 bim_element: pos_x has unknown class MONEY

    Fix: Use KEY, REF, MEASURE, DATE, FLAG, CODE, TEXT or OTHER.

    M8 — The same column declared twice¶

    Start from pattern P7. In the declaration of bim_element: add a second column POS_X.

    x V3 bim_element: duplicate column POS_X

    Fix: Each column once (names are not case-sensitive).

    M9 — Sending a column the system computes¶

    Start from pattern P1. In the row "F2 replenishment-down": set carries to ["M_Product_ID","M_Locator_ID","M_LocatorTo_ID","QtyEntered","C_UOM_ID","MovementQty"].

       ! system-computed columns carried: MovementQty

    Fix: Send what a person types; let the receiver compute the rest.

    M10 — A mandatory column left out¶

    Start from pattern P6. In the row "T1 bpartner-shared": set carries to ["Name","C_BP_Group_ID","IsCustomer","IsVendor","IsEmployee","IsOneTime","IsSalesRep","IsSummary","SO_CreditLimit","SO_CreditUsed","SendEMail"].

       ! mandatory columns not carried: Value

    Fix: Carry it, or be sure the receiver can supply it.

    M11 — A rule with nothing to send¶

    Start from pattern P1. In the row "R1 replenish-rule": remove emits.

       x RULE needs emits

    Fix: Name the flow the rule sends.

    M12 — A rule that names a flow that does not exist¶

    Start from pattern P1. In the row "R1 replenish-rule": set emits to "F9 replenishment-typo".

       x RULE emits names a row that does not exist: F9 replenishment-typo

    Fix: Use the exact name of the row the rule should send.

    7. When the team hears about a save — and who acts on it¶

    Background for the people who design flows. Nothing here is a setting; it explains why the rows above can be trusted. Spec: prompts/TEAM_REPLICATION_PLUGIN_STUDY.md §9–§10.

    A save is part of a transaction. One action of a user can write many records. A Complete on a sales order, for example, writes the shipment, its lines, the invoice and the accounting entries together. They form one transaction: either all of them are kept (commit) or, if anything fails near the end — a closed period, say — all of them are undone (rollback), as if they never existed.

    Legacy iDempiere announces a save early. Its "after save" notices (postCreate, postUpdate) are sent the moment each record is saved, while the transaction is still open (PO.java:2799-2804), and they are delivered a little later on another thread. If the transaction is then rolled back, a notice has already gone out about a record that never existed, and a listener reading the database may not find a record it was told about. Legacy also has a separate after-commit hook (Trx.addTrxEventListener → afterCommit, Trx.java:452,761) that careful code can use; the standard notices do not use it.

    The twin announces a save once, after the commit. In the SQLite twin one user action becomes one op group, and the kernel commits the whole group in one step. Observing listeners are told after that step succeeded — exactly once, in a fixed order, and never for a group that was rolled back. The screens and messages are the same as legacy; only this behind-the-scenes moment is defined more strictly.

    Why replication needs exactly that. Sending a team member's changes to the others is such an observing listener. If it could see a save that was later undone, it would send a ghost document to the whole team — a second source of truth. Told only after the commit, it can only ever send what really happened.

    A received record is saved as a replica, and that is a different event. When a device takes in a record from another device, it saves it as a replica (legacy po.saveReplica(true)), and the save raises its own events — after new replication, after change replication, before delete replication — instead of the ordinary after new / after change / before delete (PO.java:2785-2787, 4300). A process chain that must run where the declaration ARRIVES — head office turning a station's sale lines into one completed order with Import Orders (pattern P1) — listens to after new replication. The station's own save of its sale lines raises only the ordinary after new, so the chain never runs at the station: one document, one Complete, at head office only.

    What the team layer may and may not do. It carries, orders and admits changes, and it stores what it receives as data. It never completes, posts, numbers or authors a document, computes stock, price or tax, or decides access in its own code; those are the core's, and team rules are expressed as data the core already understands (for example Document Action Access rows).

    Status, 2026-10-27: designed and specified (study §9–§10); the one event bus that delivers these moments, with the replica save, is being built (study §10.5 will record the result). Until it lands, the live team layer observes commits through its own built-in hook, which already runs only after the committed rows are written to the device's store (bim-ootb erp/crud_overlay.js _sidePersist → _teamPush, :1937).

    8. Principles behind this design — for anyone building something similar¶

    Distilled 2026-10-27 from the team-layer work (prompts/TEAMWORK_FRAMEWORK.md §38, prompts/TEAM_REPLICATION_PLUGIN_STUDY.md §8–§10). Each one is a rule this project already enforces, not a wish.

    1. Twin before you innovate. Copy the legacy mechanism exactly; a difference found by running both side by side is fixed on the new side. Users see no change, so adopting it costs them nothing.
    2. Every server rule becomes signed data. One completer per document, who may use which document action, which keys are trusted, which translation rules apply — each is an owner-signed policy inside the shared log, judged the same way by every device. No referee in the middle.
    3. Declare where the action happens, derive in one place. A point of sale only declares its lines; one processor completes once and returns what is needed. Mistakes show up as consequences (under-declaring starves your own replenishment), not as online checks.
    4. Send the minimum. Ids, references, quantities and codes. Every device already holds the master data, so meaning never travels.
    5. Separate by permission, not by promise. A plugin is given only the hooks its job needs. The team layer may observe saves and store what it receives; it is structurally unable to complete, post or number a document.
    6. Rows over code. Flows, listeners and access are dictionary rows, never per-window code; progress is counted as X of N over the whole dictionary, never one hand-picked demo.
    7. A log line is the proof, not a screenshot. Every change starts with a test that fails; every deliberately broken copy must make it fail (a crash does not count); a test that judged nothing says INCONCLUSIVE, never PASS.
    8. Never silently break users. A change that would invalidate existing teams (for example the shared base fingerprint) needs an upgrade path or an openly stated consequence before it ships.

    9. What this guide does not cover yet¶

    • All rows here are samples. Nobody has authored real business flows yet; the business owner decides what really moves.
    • Only the Modeller and the ERP team scope read their plan in the live applications today. The point-of-sale and micro-finance patterns run in the simulator.
    • The plans that ship are not signed by default. Signing works (build/scriptor/sign_plan.js) and a team pins the keys it trusts when it is founded; every member of a team can still read everything in that team (audience keys are not built).
    • The compiler checks names and shapes. It cannot know whether a row is a good business decision.
